# MYSEOULDROP 모바일 디자인 학습·전수 검수 시스템 설계

> 작성일: 2026-08-15  
> 상태: 사용자 승인 완료, 구현 계획 작성 전  
> 적용 범위: 루트 MYSEOULDROP 모바일 웹앱  
> 격리 원칙: 이 설계와 후속 산출물은 `design-lab/`에만 저장하며 기존 서비스에 자동 반영하지 않는다.

## 1. 목적

MYSEOULDROP의 출시 전 디자인 품질을 페이지 단위가 아니라 실제 사용자 플로우와 화면 상태 단위로 검수한다. 동시에 모바일 레퍼런스에 대한 사용자의 선호·비선호를 축적해, 이후 검수와 개선 제안이 사용자의 취향에 점차 가까워지도록 한다.

이 시스템은 두 가지 결과를 함께 만든다.

1. 모든 활성 페이지, 상세 화면, 모달, 드로어, 바텀시트와 주요 상태를 빠짐없이 확인할 수 있는 전수 검수 체계
2. 사용자의 선택과 이유를 반복 가능한 디자인 판단 기준으로 전환하는 취향 학습 체계

## 2. 확정된 디자인 취향

### 2.1 대표 테마

- 라이트 테마를 대표 디자인과 시각 품질 판정 기준으로 사용한다.
- 다크 테마는 기능 및 레이아웃 회귀 검사 대상으로 유지한다.

### 2.2 핵심 작업 화면

- 지도, 검색, 필터, 길찾기처럼 사용자가 즉시 행동해야 하는 화면은 `도시 현장형` 방향을 따른다.
- 지도 면적, 빠른 탐색, 높은 정보 밀도와 명확한 조작을 브랜드 연출보다 우선한다.
- 핵심 플로우에 설명성 카드나 부가정보를 과도하게 노출하지 않는다.
- 화면의 목적과 다음 행동이 3초 안에 이해되어야 한다.

### 2.3 선택적 콘텐츠 표현

- 큰 제목, 넉넉한 여백, 오른쪽 썸네일, 구분선 중심 목록으로 구성된 에디토리얼 표현을 선호한다.
- 이 표현은 특정 기능이나 콘텐츠 종류로 확정하지 않는다.
- 실제 정보성 콘텐츠가 필요하고 핵심 조작을 방해하지 않을 때만 선택적으로 사용한다.
- 지도와 검색 같은 작업 화면에 에디토리얼 패턴을 억지로 적용하지 않는다.

### 2.4 취향 해석 원칙

- 특정 앱을 그대로 복제하지 않는다.
- 레퍼런스는 정보 밀도, 여백, 타이포그래피, 이미지 위치, 조작 방식과 같은 속성 단위로 해석한다.
- 서로 다른 선호가 충돌할 때 하나를 삭제하지 않고 적용 맥락을 분리한다.
- 예: `높은 정보 밀도`는 지도에, `넉넉한 에디토리얼 여백`은 선택적 콘텐츠 목록에 적용한다.

## 3. 범위와 비범위

### 3.1 포함 범위

- 루트 Next.js 모바일 웹앱의 활성 사용자 화면
- 실제 사용자가 이동하는 시작·탐색·상세·저장·설정 플로우
- 동적 상세 경로와 대표 데이터 상태
- 모달, 드로어, 바텀시트, 토스트, 전체화면 오버레이
- 기본, 로딩, 빈 화면, 오류, 권한 거부와 긴 텍스트 상태
- 360px, 390×844, 430px 모바일 화면
- 라이트 테마 시각 검수와 다크 테마 회귀 확인
- 현재 구현과 향후 추가되는 화면·상태의 지속적 인벤토리화

### 3.2 제외 범위

- `essenly-homepage` 랜딩 사이트
- 사용자 승인 전 기존 서비스 코드 수정
- 미정 콘텐츠를 임의로 확정하거나 새로운 기능으로 간주하는 작업
- 운영 데이터, 예약, 결제 등 디자인 검수를 넘어서는 제품 구현
- 레퍼런스 앱의 화면을 그대로 복제하는 작업

## 4. 격리 구조

모든 학습·검수 산출물은 프로젝트 루트의 `design-lab/` 아래에만 저장한다. 이 디렉터리는 Git에 포함하지만 앱 실행 경로와 연결하지 않는다.

예정 구조:

```text
design-lab/
├── README.md
├── taste-profile.md
├── preference-log.jsonl
├── qa-matrix.md
├── review-playbook.md
├── references/
├── findings/
├── reports/
└── specs/
    └── 2026-08-15-mobile-design-learning-and-audit-system.md
```

### 4.1 기존 서비스 보호 규칙

- `design-lab/`에서 `app/`, `components/`, `lib/`를 런타임 의존성으로 import하지 않는다.
- `design-lab/`을 앱 라우트, 빌드 설정, Tailwind 콘텐츠 경로 또는 배포 설정에 추가하지 않는다.
- 기존 `.impeccable.md`, `AGENTS.md`, 디자인 시스템 문서와 서비스 코드는 수정하지 않는다.
- 검수 중 발견한 개선안은 `findings/`에 제안으로만 기록한다.
- 서비스 반영은 사용자가 특정 개선안을 별도로 승인한 이후의 독립 작업으로 진행한다.
- 후속 Git 커밋은 작업 목적에 맞는 `design-lab/` 파일만 명시적으로 스테이징한다.

## 5. 저장 모델

### 5.1 `taste-profile.md`

현재까지 확정된 취향만 사람이 읽기 쉬운 형태로 요약한다. 관찰 한 번으로 바로 갱신하지 않고 반복된 선택이나 사용자 명시 승인이 있을 때 변경한다.

각 취향은 다음 속성을 가진다.

- 규칙
- 적용 화면 또는 맥락
- 피해야 할 해석
- 근거가 된 선택
- 확신 수준
- 마지막 확인일

### 5.2 `preference-log.jsonl`

레퍼런스 선택과 사용자 피드백을 시간순으로 추가하는 변경 불가 이력이다. 과거 기록을 덮어쓰지 않으며, 현재 결론은 `taste-profile.md`가 요약한다.

각 기록은 다음 값을 포함한다.

- 기록 시각
- 검토한 레퍼런스 또는 방향
- 선호·비선호·혼합 판단
- 사용자가 말한 이유
- 추출한 디자인 속성
- 적용 가능 화면
- 상태: `observation`, `hypothesis`, `confirmed`, `superseded`

### 5.3 `qa-matrix.md`

페이지 목록이 아니라 `플로우 × 화면 × 상태 × 화면 크기 × 테마`를 추적한다.

각 행은 다음 정보를 가진다.

- 고유 검수 ID
- 사용자 플로우
- 경로와 진입 조건
- 화면 또는 오버레이
- 데이터·권한·인증 상태
- 검수 화면 크기와 테마
- 기대 동작과 시각 기준
- 최근 결과
- 증거 위치
- 연결된 발견 항목
- 다음 검수 조건

### 5.4 `findings/`

문제 또는 개선 가설마다 독립 파일을 생성한다. 하나의 발견이 여러 화면에 영향을 주면 파일 하나에서 영향 범위를 연결한다.

각 발견은 다음 정보를 가진다.

- 고유 ID와 제목
- 분류: 오류, 사용성, 일관성, 접근성, 시각 개선, 새로운 가능성
- 심각도: 출시 차단, 높음, 일반, 미세 조정
- 관찰 내용과 재현 조건
- 사용자에게 미치는 영향
- 화면 증거
- 관련 취향 또는 디자인 원칙
- 개선 가설
- 예상 이득과 부작용
- 상태: `observed`, `proposed`, `approved`, `implemented`, `verified`, `deferred`, `rejected`
- 결정 및 재검증 이력

### 5.5 `references/`

참고 앱이나 화면을 앱 이름만으로 기록하지 않는다. 어떤 문제를 해결하기 위해 참고했는지, 무엇을 선호하거나 거부했는지 함께 기록한다.

현재 초기 레퍼런스 축은 다음과 같다.

- 지도·현장 탐색: KakaoMap, NAVER Map, Google Maps
- 여행 발견·편집: Airbnb, Wanderlog
- 뷰티 발견·거래: Olive Young Global, Booksy, UNNI

## 6. 취향 학습 수명주기

취향은 다음 단계를 거친다.

```text
레퍼런스 또는 실제 화면 관찰
  → 사용자의 선택과 이유 기록
  → 디자인 속성 단위의 가설 생성
  → 다른 화면과 레퍼런스에서 반복 확인
  → 사용자 승인
  → 확정 취향으로 승격
  → 이후 검수와 제안에 적용
```

운영 규칙:

- 선택 결과만 기록하지 않고 이유를 함께 수집한다.
- 사용자가 이유를 말하지 않은 선택은 낮은 확신의 관찰로 남긴다.
- 확정 취향과 충돌하는 새 선택은 오류로 취급하지 않고 적용 맥락 차이를 먼저 확인한다.
- 콘텐츠가 미정이면 레이아웃과 시각 패턴만 기록한다.
- 새 정보가 과거 판단을 대체해도 과거 기록은 유지하고 `superseded` 상태로 연결한다.

## 7. 전수 검수 모델

### 7.1 핵심 플로우

1. 진입 → 로그인 또는 게스트 → 온보딩
2. 지도 → 카테고리·필터 → 장소 선택 → 장소 상세 → 외부 길찾기
3. 지도 → 지하철 모드 → 역 검색·경로 → 역 주변 장소 탐색
4. 검색 → 결과 → 지도 복귀 또는 상세 이동
5. 랭킹 → 상품 상세 → 판매처 또는 지도 탐색
6. Saved → 카테고리 전환 → 항목 해제 → 재진입
7. My → 프로필 → 설정·지원·법무

### 7.2 상태 축

- 기본
- 로딩
- 빈 화면
- 오류와 복구
- 위치 허용·거부·재시도
- 로그인·게스트·세션 만료
- 검색 결과 있음·없음
- 긴 영문, 한국어 원문, 긴 주소
- 약한 네트워크와 외부 앱 미설치
- 키보드 노출과 200% 확대

### 7.3 오버레이 축

- 지도 결과 시트
- 필터 바텀시트
- 지하철 플래너와 검색 오버레이
- 예약·채널 안내 시트
- 피드백 시트
- 햄버거 드로어
- 로그아웃·계정 삭제와 기타 확인 모달
- 토스트와 상태 알림

각 오버레이는 열기, 내부 스크롤, 배경 스크롤 잠금, 키보드, 중첩, 닫기, Escape, 포커스 이동과 복원을 확인한다.

### 7.4 화면 크기와 테마

- 360px: 작은 기기에서 잘림, 가로 스크롤과 터치 영역 검사
- 390×844: 대표 모바일 시각 판정
- 430px: 큰 모바일에서 밀도와 여백 검사
- 라이트 테마: 시각 품질과 취향 일치 판정
- 다크 테마: 주요 동작과 레이아웃 회귀 검사

## 8. 검수 회차

각 회차는 같은 순서를 따른다.

1. 인벤토리 갱신
2. 핵심 플로우 주행
3. 360px·390px·430px 시각 검수
4. 상태와 엣지 검수
5. 동일 목적의 모바일 레퍼런스 조사
6. 발견 사항 분류와 개선 가설 작성
7. 사용자 승인
8. 별도 서비스 구현
9. 동일 조건 재검증
10. 취향 프로필과 검수 플레이북 갱신

검수 중 새로운 페이지, 상태, 오버레이 또는 문제 유형을 발견하면 해당 회차에서 인벤토리와 플레이북에 추가한다. 최초 분류 체계에 맞지 않는다는 이유로 발견을 누락하지 않는다.

## 9. 레퍼런스 사용 원칙

레퍼런스 조사는 다음 세 층으로 해석한다.

1. 범주 기본기: 해당 앱 종류에서 사용자가 이미 기대하는 패턴
2. 현재 흐름: 최근 제품들이 채택하는 정보 구조와 상호작용
3. MYSEOULDROP 맥락: 외국인 여행자가 서울 현장에서 빠르게 행동해야 한다는 조건

레퍼런스를 적용할 때는 다음 질문에 답한다.

- 어떤 사용자 문제를 해결하는가?
- MYSEOULDROP의 현재 플로우에도 같은 문제가 있는가?
- 사용자가 선호한 속성은 무엇인가?
- 무엇을 가져오지 않아야 하는가?
- 적용 시 핵심 작업 속도나 정보 신뢰가 떨어지지 않는가?

## 10. 안전장치와 실패 처리

- 브라우저 연결 또는 로컬 URL 열기가 한 번 실패하면 같은 방법을 반복하지 않고 즉시 실행 가능한 터미널 명령을 제공한다.
- 인증이나 특정 데이터가 없어 확인하지 못한 상태는 통과로 표시하지 않고 `검수 보류`로 기록한다.
- 화면 캡처에 계정 정보나 민감한 데이터가 포함되면 장기 보관하지 않는다.
- 레퍼런스 링크가 사라지면 대체 자료를 추가하되 기존 선택 이력은 유지한다.
- 자동 발견 결과는 검수 후보일 뿐이며 실제 활성 화면 여부를 확인한 뒤 매트릭스에 포함한다.
- 새로운 개선안은 기존 서비스에 자동 반영하지 않는다.
- 검수 도구의 실패를 제품 결함으로 기록하지 않는다.

## 11. 초기 관찰 항목

2026-08-15, `http://127.0.0.1:3000/map`을 390×844 라이트 테마로 캡처한 결과 다음 후보를 발견했다.

1. 오른쪽 상단 조작 요소와 하단 `My` 탭이 화면 밖으로 잘리는 것으로 보인다.
2. 지도 나침반 컨트롤이 하단 `Map` 탭과 겹친다.
3. 결과 시트의 첫 장소 행이 고정 하단 내비게이션에 가려진다.
4. 많은 핀과 색상이 동시에 노출되어 선택 우선순위가 약해질 가능성이 있다.

이 항목들은 구현 결함으로 확정하지 않는다. 후속 검수에서 재현 조건, 실제 DOM 크기, 스크롤 상태와 다른 모바일 너비를 확인한 뒤 `findings/`에 정식 등록한다.

## 12. 완료 기준

설정 구현은 다음 조건을 모두 만족할 때 완료한다.

- 활성 페이지가 하나 이상의 사용자 플로우와 연결되어 있다.
- 모든 모달·드로어·시트와 주요 화면 상태가 인벤토리에 있다.
- 360px, 390px, 430px 라이트 테마 검수 상태를 기록할 수 있다.
- 문제마다 증거, 영향도, 개선 가설과 승인 상태를 남길 수 있다.
- 확정 취향과 검증 중인 가설이 분리되어 있다.
- 새 페이지와 새로운 문제 유형을 기존 기록을 깨지 않고 추가할 수 있다.
- 다음 검수에서 이전 결과와 비교할 수 있다.
- `design-lab/`을 제거해도 기존 서비스 실행, 테스트와 빌드 결과가 달라지지 않는다.

## 13. 후속 구현 범위

이 설계 승인 후 별도 구현 계획에서 다음 작업을 세분화한다.

1. `design-lab/` 디렉터리와 기본 문서 생성
2. 현재 라우트·오버레이 인벤토리 작성
3. 취향 프로필과 초기 선호 로그 작성
4. 발견 항목 템플릿과 검수 보고서 템플릿 작성
5. 기존 서비스에 영향을 주지 않는 읽기 전용 인벤토리 검사 방식 정의
6. 첫 전수 검수 회차 실행 계획 작성

서비스 코드 수정과 실제 디자인 개선 구현은 이 범위에 포함하지 않는다.
