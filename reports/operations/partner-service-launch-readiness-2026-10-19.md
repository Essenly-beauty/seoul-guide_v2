# 실서비스 운영 요건 검토 — 파트너 예약 (2026-10-19)

사용자 질문 "환불이나 이런 건 어떻게 해주는 건가요"와 "실제 서비스 운영에 필요한 내용이 전체적으로 모두 들어가면 좋겠다"에 대한 검토. 시안(v3.2)과 승인된 설계([예약 운영 개정안](../../docs/superpowers/specs/2026-10-18-partner-reservation-operations-design.md), [관리자·예약 설계](../../docs/superpowers/specs/2026-10-18-partner-admin-booking-design.md))를 기준으로, 실제로 돈과 예약이 오가는 운영에 무엇이 더 필요한지 영역별로 적었다. 법·세무 항목은 전문가 확인이 필요한 것으로 표시했다.

상태 표기: ✅ 구현됨 · 🟡 시안에 있음(구현 전) · ⚪ 설계 문서에만 있음 · ❌ 아직 없음 · ❓ 결정 필요

## 0. 결론

관리자 **화면**은 시안으로 대부분 갖춰졌다(캘린더·목록·고객·출근표·메시지·통계). 실제 운영에 부족한 것은 화면이 아니라 **돈의 흐름(결제·환불·정산)**, **정책과 계약**, **운영팀이 쓸 콘솔**, **고객 앱 쪽 예약 완성**, **알림 인프라**, **개인정보 규칙**이다. 이 여섯 가지 중 먼저 정해야 할 결정 5개를 4절에 모았다. 결정이 나면 파일럿 업체 3곳 기준의 최소 세트(3절)를 구현한다.

## 1. 환불은 어떻게 되나

### 지금 상태

- 결제·환불은 **아직 구현되지 않았다**. 고객 앱의 예약 화면에 보이는 "Deposit 25%, full refund up to 24h"는 데모 문구이지 정책이 아니다(`components/booking/booking-sheet.tsx`, `cancel-booking-button.tsx`는 "Demo only").
- 승인된 설계가 정한 원칙: 예약금은 **총 시술금액에서 차감**(방문 후 돌려주는 보증금 방식 아님), **즉시 확정**, **예약 상태와 결제·환불 상태를 분리**(취소된 예약에 "환불 처리 중/실패"가 남을 수 있고 실패는 재처리), **노쇼·예약금 몰수는 업체가 명시적으로 처리**(시간이 지났다고 자동 몰수 안 함), 결제 화면 복귀만으로 확정하지 않고 결제사 서버 확인 후 확정.

### 제안하는 흐름

| 상황 | 누가 | 무엇이 일어나나 | 관리자 화면 |
| --- | --- | --- | --- |
| 고객이 앱에서 취소 | 고객 | 서버가 환불 정책표로 환불률 계산 → 결제사 취소 API(전액/부분) → 카드사 환불(보통 3~7영업일) → 예약 "취소" + 환불 상태 "처리 중 → 완료" → 고객·업체 알림 | 예약 목록 취소 탭에 환불 상태 칩, 상세에 환불 금액·완료일 |
| 업체가 취소(매장 사정) | 업체 | 사유 필수(고객에게 보임) → **전액 환불 자동** → 고객 알림 | 시안의 취소 확인 상자 그대로 |
| 노쇼 | 업체 | 시작 시간 후 업체가 명시적으로 처리 → 예약금은 업체 귀속(정산에 포함) → 고객 안내. 고객 이의 제기 시 운영팀이 수동 환불 | 시안의 노쇼 확인 상자 + "되돌릴 수 없음" |
| 시간 변경 | 양쪽 | 환불 없이 예약금 유지(같은 예약번호) | 시안의 끌어서 옮기기·시간 변경 |
| 결제 실패·중복 결제·점유 만료 후 늦은 결제 | 시스템 | 자동 확정하지 않고 "운영팀 확인" 큐로. 중복 결제는 자동 환불 | 운영팀 콘솔(5절 E) |
| 분쟁(시술 불만 등) | 운영팀 | 업체 정산 전이면 보류 후 판단, 정산 후면 업체에 차감 | 운영팀 콘솔 |

### 아직 정해지지 않은 것 ❓

1. **환불 스케줄**: 예) 방문 전날 18시까지 전액, 당일 취소 0%. 네이버 예약은 방문 10일 전부터 일자별 환불률을 쓴다. 단순할수록 분쟁이 적다 → 2단계(전날까지 100% / 당일 0%)를 권장.
2. **예약금 금액**: 정액(예: 1만 원) vs 비율(예: 20%). 관광객 대상이면 **정액**이 설명하기 쉽다.
3. **돈을 누가 받나**: (a) 플랫폼이 예약금을 받고 업체에 월 정산(수수료 차감) vs (b) 업체가 각자 결제사 계약으로 직접 수납. (a)가 고객 경험과 환불 통제에 유리하지만 아래 법무 확인이 필요하다.
4. **환불 수수료와 결제 수수료 부담**: 결제사 수수료(약 2~3%, 해외카드는 더 높음)는 환불 시 돌려받지 못하는 경우가 많다. 누가 부담할지.
5. **결제사 선정**: 고객이 외국인이므로 **해외 발급 카드·Apple Pay·Google Pay**가 필수. 국내 결제사(토스페이먼츠·KG이니시스 등)의 해외카드 옵션 또는 Stripe. 원화 결제로 통일하고 DCC(현지 통화 자동 변환)는 피한다.

### B. 고객 앱 예약 여정

| 항목 | 상태 | 비고 |
| --- | --- | --- |
| 업체 상세 → 메뉴 → 디자이너 → 날짜·시간 → 확인 → 결제 → 확정 | ⚪ | 현재 `booking-sheet.tsx`는 고정 데이터 데모. 디자이너 선택 단계 없음 |
| 실시간 가용 시간(매장∩디자이너−휴게−차단−기존 예약, 동시 수용) | ⚪ | 서버 계산 API 필요. 시안의 계산식과 같게 |

| 항목 | 상태 | 비고 |

### D. 정책·계약·법무 ❓ (전문가 확인 필요)

- 업체 제휴 계약서: 수수료, 정산 주기, 노쇼 예약금 귀속, 취소 책임, 분쟁 처리, 개인정보 위탁/제3자 제공 범위.
- 고객 약관·개인정보처리방침 개정: 예약·결제·환불 조건, 업체에 제공되는 고객 정보 항목, 메시지 보관.
- 플랫폼이 예약금을 받고 정산하는 구조라면 통신판매업 신고와 **통신판매중개자 고지**, 결제대금 보관 방식(결제사 에스크로 활용 여부)을 법무에 확인. 업체 직접 수납 구조라면 업체별 결제사 가입이 필요해 온보딩이 무거워진다.
- 노쇼 예약금 몰수 조항은 약관에 명시해야 분쟁에서 방어 가능.
- 외국인 고객 결제 고지(통화, 수수료), 영문 약관.

### G. 메시지

- 테이블(`conversations`·`messages`), RLS, Supabase Realtime 구독, 신고·차단, 보관 기간, 운영팀 열람 권한. 예약에 묶인 대화만 허용(자유 채팅 아님). 🟡 → ❌(구현)

### H. 고객 데이터·개인정보

- 업체가 보는 항목 최소화(이름·연락처·요청사항·방문 이력). 연락처 마스킹 시점(네이버 6개월), 삭제 요청 처리, 업체 메모의 민감정보 금지 안내, 외국인 고객 정보의 처리 위치(Supabase 리전) 고지. ❓ 보관 기간

### I. 보안·권한

- 업체별 격리(RLS) ✅, 감사 로그 ✅. 추가: 직원 계정·역할, 관리자 세션 만료, 결제 웹훅 서명 검증, 운영팀 권한 분리, 백업·복구 절차.

### J. 다국어

- 고객 앱 영어(일본어 예정) ↔ 관리자 한국어. 메뉴명 한/영 입력(설계 ✅), 자동 안내 메시지 영/일 템플릿, 고객 메시지는 원문 그대로 + 번역 보조(2단계).

### K. 운영 절차·지표

- 런북(결제 실패, 중복 예약, 업체 휴무 급변, 결제사 장애), CS 응답 목표(메시지 1시간 내 등), 지표(예약 전환율, 취소율, 노쇼율, 환불 처리 시간, 메시지 응답 시간), 월간 업체 리포트.

### L. 업체 온보딩

- 가입 → 사업자·매장 확인 → 계약 동의 → 메뉴·디자이너·근무시간 설정(가이드) → 테스트 예약 → 운영팀 공개 승인. 시안의 홈 "접수 준비 4단계"가 이 흐름의 업체 쪽 화면.

### M. 리뷰·평점

- 앱 리뷰(`ratings`) ✅ 존재하나 업체↔장소 연결이 없어 관리자에 표시 불가. 연결 후 조회·답글(답글은 약관·운영 정책 필요).

### N. 테스트·출시

- 결제사 샌드박스로 결제·환불·중복·만료 시나리오, 업체 2계정 격리, 파일럿 업체 3곳 2주 운영 후 공개.

## 3. 출시 최소 세트 제안 (파일럿 3곳, 수동 운영 허용)

1. 예약 저장 테이블 + 상태 전이 + 가용 시간 API
2. 고객 앱 예약 여정(디자이너 선택 포함) + 내 예약·취소
3. 결제사 1곳 연동(해외카드 포함) + 예약금 결제 + 즉시 확정 + 정책 1종 자동 환불
4. 관리자: 캘린더·예약 목록·고객·출근표(시안 그대로) + 결제·환불 상태 표시
5. 알림: 고객 이메일+푸시, 사업자 푸시(알림톡은 2단계)
6. 운영팀: 수동 콘솔(Supabase 대시보드 + 체크리스트), 환불 예외 수동 처리

8. 정산: 월 1회 수동 명세·송금

2단계: 메시지 실시간, 통계, 정산 자동화, 알림톡, 리뷰 답글, 직원 계정, 일본어.
