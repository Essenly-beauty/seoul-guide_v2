# 업체 관리자·예약 연동 진행 기록

날짜: 2026-10-18

## 현재 상태 — 예약 운영 범위 개정 승인

아래 A1/A2 및 R1 항목은 당시 검증 결과를 보존한 이력이다. 최신 범위는 **운영팀의 일반 정보·사진 관리 / 업체의 예약 메뉴·패키지·담당자·일정 관리**로 책임을 구분한다. 자유 컬럼·CMS는 제외한다. 사용자는 `2026-10-18-partner-reservation-operations-design.md`의 개정안을 승인했다.

### 최신 상태 — R3 담당자 저장 기반 로컬 검증

- `cd2859d`–`95e7282`에서 업체별 선택적 담당자, 담당 메뉴 연결, 담당자 근무·휴무/특별 날짜를 저장하는 세 테이블과 검증·권한·감사 훅을 추가했다. 담당자는 로그인 계정이 아니다. 업체가 메뉴와 담당자 연결을 명시하며, 다른 업체의 메뉴/담당자를 연결할 수 없다. 직접 인증 Data API에서도 담당자당 메뉴 1,000개 상한과 일정 256 KiB 제한을 검사한다. `booking_enabled=false`는 유지한다.
- 독립 사양·품질 검토를 각각 통과했다. visible 담당자 이름의 유니코드 공백 검사를 앱의 JavaScript `trim()`과 맞췄다. 로컬 일회용 QA DB에서 새 pgTAP 284/284, 현재 작업 트리의 SQL 6개 파일 552/552, 앱 1,723/1,723, 타입 검사·린트·diff 검사가 통과했다. DB advisor 경고는 기존 17개로 동일하고 새 담당자 테이블 경고는 없었다. 이번 DB 단위 후 배포용 빌드를 다시 돌리지는 않았으며, 이전 R2 빌드 58개 경로 통과 기록만 있다.
- 마이그레이션은 API 54381/DB 54382와 정확한 QA 컨테이너를 확인한 후 그 일회용 로컬 DB에만 단일 트랜잭션으로 직접 적용했다. 따라서 QA의 Supabase migration ledger에는 이 파일의 적용 기록이 없다. 새 세 테이블과 RLS·복합 FK·트리거를 읽기 전용으로 재확인했다. 운영 DB에는 미적용이며 원격 push·배포도 하지 않았다.
- **QA 데이터 예외:** 지속성 확인 중 신규 격리 업체 대신 기존 일회용 QA 업체 `5602a817-a6b2-4848-942c-a1e0d22e5f0f`에 테스트 담당자 `f4000000-0000-0000-0000-0000000000a5`, 메뉴 연결 1건, 일정 1건이 저장되고 감사 이벤트 3건이 남았다. 기존 업체의 기본 정보·멤버십은 수정하지 않았고, 다른 업체 계정에서는 세 기록 모두 보이지 않았다. 격리 fixture 원칙에는 어긋나므로 이 검증을 “깨끗한 QA”로 표시하지 않는다. 기록·감사 이력은 임의 삭제하지 않았다.
- 아직 담당자 API/관리 화면 및 고객 예약 가능 시간 조회와 연결되지 않았다. 다음 수직 단위는 동일 업체 ID와 R1 계약을 쓰는 `staff`/`staffMenu`/`staffSchedule` 명령·조회와 `/partner/staff` 편집기다. 담당자 1,000개 연결 제한의 동시 2세션 회귀 테스트는 추가로 필요하며, 현재 구현은 PostgREST 기본 READ COMMITTED 직접 쓰기 범위다. 예약 활성화에는 기존 매장 설정을 포함하는 DB 원자적 점유, 결제·취소/환불, 업체 현황, 운영 계약이 여전히 필요하다.
- 운영 반영 전 `merchant_services(merchant_id,id)` UNIQUE 제약의 잠금 시간·롤백과 R2의 기존 일정 CHECK 호환성을 사전 점검하고, 마이그레이션 적용 순서를 확정해야 한다. 장소 감사 보고서가 오래되어 `npm run audit:data:check`는 여전히 사전 배포 게이트이며 이 단위에서 다시 생성하지 않았다.

### 남은 검증과 통합

1. 담당자·담당 메뉴·근무·휴무 저장 기반은 로컬 QA에서 검증했다. 다음 단위에서 이를 업체 API·관리 화면과 연결하고 같은 예약 가능 시간 계산에 연결해야 한다. 담당자 로그인 계정 발급은 이 범위가 아니다.
2. 그다음 고객 선택 화면과 관리자 설정을 동일 서버 조회로 연결하고, 원자적 점유·결제 검증·즉시 확정·취소/환불·업체 예약 현황을 같은 예약번호로 검증해야 한다. 지금은 실제 예약 기능이 아니다.
3. 기존 서비스 품질 작업의 A3 잔여 브라우저 QA와 장소 감사 보고서 갱신 원인 검토가 필요하다. 특히 `npm run audit:data:check`가 실패하므로 전체 사전 배포 검증은 아직 통과하지 못했다.
4. 운영 마이그레이션 사전 점검·적용 순서·잠금/롤백 계획, 실제 업체 연결 승인, 결제사 테스트 및 사용자의 최종 배포 확인이 남아 있다. 원격 push·배포는 하지 않았다.

- `/private/tmp/partner-db-20261018-GtGZtZ`에 별도 프로젝트를 생성했다. DB 54342 / shadow 54340을 사용하고 시드를 비활성화했으며, 기존 마이그레이션만 복사해 빈 DB에 적용했다. 이 테스트 환경에서만 A2 저장 구조를 작성한다.
- A2 시작 전 기존 앱 테스트 118개 파일 / 1,127개 통과를 다시 확인했다. 첫 pgTAP 검사는 새 테이블 6개가 없는 것을 정확히 실패로 검출했다. 저장 구조의 구현·보안 검토·새 DB 재적용 검증과 앱 계정 삭제 보호 구현·최종 통합 검토를 완료했다.
- Docker 외의 native runtime도 공식 문서에서 확인했지만 실험 기능·별도 환경 구성이 필요하므로 자동 전환하거나 CLI를 업그레이드하지 않았다. [공식 런타임 가이드](https://supabase.com/docs/guides/local-development/docker-and-native-runtimes)
- 운영 DB, 실제 업체 권한, 결제 제공업체 설치, 원격 push, 배포는 변경하지 않았다.

브랜치와 분리 작업 공간을 보존한다. 기존 서비스 품질 개선의 미완료 항목 및 배포 전 검증도 그대로 남아 있다.

## A2 저장 계층 검증 기록 — 검토 완료

- 마이그레이션 `20261018080122_partner_configuration.sql`을 CLI로 생성했다. 업체·소유권·카테고리·메뉴·영업시간·감사 이력 6개 테이블에 RLS와 열 단위 쓰기 권한을 적용했다.
- 승인 전 예약 공개는 DB 제약으로 차단한다. 예약금·운영 상태·소유권은 업체 계정이 바꿀 수 없고, 일반 정보·메뉴·영업시간만 권한에 맞게 편집한다.
- 시간표 저장 한도는 영업 구간 128개, 휴게 구간 128개, 날짜별 차단 512개, 합계 JSON 텍스트 256 KiB다. A3 입력 검증과 안내에 이 한도를 반영해야 한다.
- 첫 번째 생성본의 권한 부여 순서 오류를 새 DB 재적용 테스트에서 발견했다. 테이블 권한 회수 뒤 열 단위 권한 부여가 오도록 수정했다. CLI가 누락한 명시적 권한 회수도 포함했다.
- 새 재적용 환경: `/private/tmp/partner-replay-20261018-jNloje`, DB 54362 / shadow 54360. 전체 기존 마이그레이션부터 적용했다. 독립 사양 검토에서 요청한 테스트 3건을 보강하고, 품질 검토에서 발견한 Unicode 문자 수 계산 차이도 수정했다. 최종 pgTAP 3개 파일 / 170개(신규 158개 + 기존 12개), 공유 도메인 테스트 42개 통과. 사양·품질 검토 모두 재승인됐고 열린 지적 사항은 없다.
- 검사 종료 후 auth 사용자·업체·감사 이력은 모두 0건이다. 테스트 픽스처는 트랜잭션 롤백으로 남기지 않았다.
- 자동 검사 결과: 오류 0건, 새 경고 0건. 기존 경고 17건(권한 함수 호출 최적화, 기존 `touch_updated_at` search path, `web_vitals` 수집 정책)은 별도 기존 품질·배포 전 점검 대상이다.
- A3의 저장 요청은 허용 필드만 명시해야 한다. 예약금 null이나 식별자를 통째로 포함하는 범용 업데이트/upsert 대신, 신규 행 생성과 기존 행의 허용 열 수정을 구분한다.
- 문자열 제한은 PostgreSQL과 동일한 Unicode 코드 포인트 수로 센다(이름 120, 설명 4,000). 기존 JS UTF-16 단위 계산과 다른 것을 재현하는 실패 테스트 후 수정했다. A3의 길이 안내도 같은 기준을 사용한다.
- 저장 계층 커밋 `b96ec1c`, 테스트 보강 `b99e64b`, Unicode 계약 정렬 `0253bb9`. 모두 `gksaudrhks12-sys` 작성자로 로컬 브랜치에 보존했다.

## A2 계정 삭제 보호 — 최종 검토 완료

- `app/api/account/delete/route.ts`에서 인증된 세션으로 자신의 소유권만 조회한 후 삭제를 판단한다. 사용자 입력 ID나 서비스 역할 조회로 권한을 우회하지 않는다.
- 소유권이 있으면 활성·철회 여부와 관계없이 409 및 `/support` 안내를 반환하고 계정 삭제나 로그아웃을 실행하지 않는다. DB 외래 키도 실제 사용자 삭제를 차단해 사전 확인 이후의 소유권 부여 경쟁을 보호한다.
- 조회 실패·통신 오류·잘못된 응답이면 503으로 실패를 알리며 삭제하지 않는다. 소유권이 없는 일반 사용자의 기존 삭제 흐름은 유지한다.
- 커밋 `76b9ebd`. 기존 코드에서 10개 실패 / 4개 통과를 관찰한 후 구현했고, 관련 테스트 14개가 통과했다. 사양·품질·최종 통합 검토 모두 승인됐고 Critical/Important/Minor 지적 사항은 없다. 마지막 검토자가 실제 소유권 SELECT 정책·쓰기 권한·auth 사용자 삭제 RESTRICT 외래 키의 연계를 별도로 확인했다.
- 메인 에이전트 최종 실행: 전체 앱 테스트 119개 파일 / 1,145개, DB 테스트 3개 파일 / 170개 통과. TypeScript·린트·diff 검사 통과. 린트의 기존 Next 명령 폐기 예정·workspace-root 안내는 남아 있다.

## A2 완료 시점의 운영 반영 게이트

당시 결과는 로컬 브랜치와 분리 DB에서 검증한 운영 기반이며, 관리자 화면·공개 예약·결제·환불을 제공하는 완성 서비스가 아니었다. A2 시점에는 실제 계정 삭제, 브라우저 통합 검사, 배포 빌드를 수행하지 않았다. 이후 A3 구현과 검증 범위는 이 문서 상단 및 A3 계획의 최신 기록을 따른다.

- 승인된 운영 마이그레이션 적용이 **계정 삭제 조회 코드 배포보다 먼저**여야 한다. 테이블이 없거나 권한 조회가 실패하면 모든 계정 삭제가 503으로 차단되는 것이 의도된 안전 동작이다. 임시 허용 fallback을 넣지 않는다.
- 운영 PostgreSQL 버전·스키마 차이, 백업·롤백 절차, 기존 경고 및 전체 서비스 품질 항목을 배포 전에 별도로 확인해야 한다.
- 운영 DB 변경, 실제 업체 소유권 부여, 원격 push, 결제 제공업체 설치, 배포는 수행하지 않았다. 기존 로컬 `mobile_design` DB도 읽기 전용 확인 외에는 변경하지 않았다.
- 개발 브랜치와 작업 공간 및 두 테스트 DB를 보존했다. 신규 SQL은 기존 DB가 아닌 별도 테스트 DB 두 곳에만 적용했다.
