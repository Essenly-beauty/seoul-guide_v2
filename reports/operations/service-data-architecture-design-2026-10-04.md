# MYSEOULDROP 서비스 데이터·운영 구조 설계

작성: 2026-10-04 · 상태: 장소 카탈로그 1단계 방향 승인, 나머지 도메인은 설계 기준 · 범위: 첫 100명 운영에서 확장 가능한 데이터 경계와 이전 순서

## 1. 결정과 범위

초기에는 기존 Supabase 프로젝트 하나를 유지한다. 계정·회원 데이터, 공개 장소 카탈로그, 커뮤니티, 미디어 메타데이터, 스토리를 **서로 다른 책임의 테이블과 접근 권한**으로 나눈다. 물리적으로 별도 DB를 만들거나, 새 CMS·분석 서비스를 도입하지 않는다. 스키마 분리 자체를 보안 경계로 간주하지 않고 `GRANT`와 RLS, 서버 권한, 운영 절차를 함께 검증한다.

이 문서는 전 도메인의 계약을 정하되 실행은 네 개의 독립 트랙으로 나눈다. 오너가 **B(장소 카탈로그)를 첫 구현 대상으로 승인**했다. B도 먼저 기존 앱 조회를 유지한 채 로컬 DB에 병행 적재·전수 비교하는 단계와, 이후 앱 조회를 전환하는 단계로 나눈다. A의 운영 접근 권한·백업 상태 확인은 B의 운영 반영 전 안전 게이트다.

1. **회원·커뮤니티 안전성:** 기존 Auth·프로필·찜·공개 리뷰·신고·공유목록의 권한, 내보내기, 삭제, 운영 조회를 먼저 확정한다.
2. **장소 카탈로그와 미디어:** 현재 생성된 정적 장소를 ID 보존 상태로 검수 가능한 공개 카탈로그에 옮긴다. 수집·검수와 앱 노출을 분리한다.
3. **스토리 연결:** 별도 블로그를 원본으로 하고 승인된 게시물만 앱에 반영한다. 블로그 플랫폼과 접근 방식 확인 전에는 연동 구현을 시작하지 않는다.
4. **상품 순위:** 기존 Google 시트·게시 스냅샷 흐름을 별도 운영 트랙으로 유지한다. 장소 DB 이전과 결합하지 않는다.

제품 랭킹 시트 수집·정기 게시, 상품 추천 기준, 예약·결제, 이미지 자동 제작, 댓글 UI, 새 관리자 대시보드는 이번 설계의 **구현** 범위가 아니다. 순위 데이터가 장소 DB와 어떻게 분리되는지는 이 문서에 명시한다. 기존 랭킹·장소 ID를 임의로 재부여하지 않는다.

## 2. 확인한 현재 상태와 한계

- 저장소의 Supabase 마이그레이션에는 `auth.users`, `public.profiles`(프로필 전체가 `jsonb`), `favorites`, `ratings`, `review_reports`, `feedback`, `shared_lists`가 있다. `ratings`는 회원·장소당 한 행이며 비공개 별점/본문과 명시적 공개 리뷰를 함께 저장한다.
- 앱 장소는 `lib/data.ts`와 생성 파일에서 조립한다. 현재 마이그레이션에는 장소 원본 테이블이 없다. `place_id`는 찜·별점·공유목록과 URL에 이미 쓰인다. 사진은 `public/places/<place-id>/`의 파일과 `lib/generated/place-photos.ts` 경로 맵으로 제공한다.
- 앱의 `/blog`는 `lib/data.ts`의 `ARTICLES` 3건을 사용한다. 기사 상세 본문은 별도 블로그와 동기화되지 않고 공통 정적 내용이다. 별도 블로그의 URL·플랫폼·발행 API는 저장소에서 확인되지 않았다. `essenly-homepage/`는 이 블로그라고 확인되지 않았으므로 연결 대상으로 가정하지 않는다.
- 상품 순위는 매장 장소와 다른 데이터 흐름이다. 공식 랭킹 운영 시트의 2026-09-27 시험 행은 게시되지 않았다. `lib/generated/published-ranking.json`의 차트는 비어 있고, 앱에는 기존 다이소 생성 스냅샷과 상품 데이터가 있다. 정기 갱신과 운영 게시가 완료됐다고 표시하지 않는다.
- 회원 프로필·게스트 프로필과 평점은 각각 Supabase와 기기 `localStorage` 사이에 동기화 경로가 있다. 기기 저장은 서버 DB의 암호화·백업·접근 제어를 제공하지 않는다. 계정별 기기 사본 정리 흐름은 유지하고 공유 기기에서 점검한다.
- 기존 공개 리뷰 뷰는 `auth.users.raw_user_meta_data`에서 표시 이름을 만든다. 이 값은 권한 판단에 쓰면 안 되며, 공개할 표시 이름의 동의·범위를 별도로 결정해야 한다. 기존 `ratings.hidden`은 사용자 수정 가능 여부를 운영 권한으로 실측하지 않았으므로 먼저 검사한다.
- 과거 운영 문서 중 `docs/data-and-integrations.md`와 `docs/user-data-strategy.md`는 인증·DB 도입 전 상태를 설명한다. 현재 구현 사실로 인용하지 않는다. 저장소의 마이그레이션이 운영 DB에 모두 적용됐다는 뜻도 아니므로 운영 스키마·정책은 읽기 전용으로 재확인한다.

## 3. 도메인별 데이터 계약

| 도메인 | 원본·예정 구조 | 접근 경계 | 운영 원칙 |
|---|---|---|---|
| 계정 | 기존 Supabase Auth `auth.users` | Auth/서버 관리자만 계정 관리. 브라우저에 비밀키 없음 | 이메일은 별도의 공개 프로필에 복제하지 않음. 비밀번호는 복호화 가능한 값이 아니라 해시로 취급 |
| 회원 프로필 | 기존 `profiles(user_id, data, updated_at)` | 회원 본인만 읽기·수정; 운영 집계는 원문 없이 최소 권한 | 첫 100명 동안 전면 정규화하지 않음. 필드별 수집 목적·선택 여부·삭제를 먼저 점검 |
| 찜·공유 | 기존 `favorites`, `shared_lists` | 찜과 목록 관리는 본인만. 공유 단건은 로그인한 수신자에게 정확한 ID로만 제공 | 장소 ID가 폐점·미게시여도 저장 행과 공유 링크 ID는 유지하고 표시 가능한 장소만 별도 계산 |
| 장소 | 신규 `places` 공개 읽기 모델 | 비회원은 `published` 행만 읽기. 쓰기는 승인된 서버/운영 흐름만 | 내부 `id text`는 불변. 영업 상태와 공개 상태를 분리; 삭제 대신 숨김/폐점 표시 |
| 장소 근거 | 신규 `place_source_records`, `place_field_evidence`, `place_revisions` | 운영자만 원본·편집 이력 열람. 공개 화면에는 허용된 출처·확인일만 투영 | 매장명·주소·좌표·영업시간·시설 등 변동 필드에 출처·관찰 시각·검수자 기록 |
| 장소 세부 | 신규 `place_hours`, `place_features`, 필요 시 `place_services` | 게시된 장소의 승인된 세부 정보만 공개 조회 | 다이소·올리브영·샵은 같은 `places`를 쓰고, 면세·유심·샵 메뉴 등만 장소별로 연결 |
| 자체 리뷰 | 기존 `ratings`, `review_reports`를 안전화 | 비회원은 공개·비숨김 읽기, 로그인 회원만 본인 작성/수정·신고, 숨김/복원은 운영자만 | 외부 지도 평점과 자체 리뷰를 다른 출처·집계로 표시. 비공개 글을 자동 공개하지 않음 |
| 외부 평점 | 권리·제공 경로 확인 후 `external_rating_snapshots` | 허용된 최신 관찰값과 출처·확인일만 공개 | Google/Kakao 등의 수치와 MYSEOULDROP 회원 평점을 합산하지 않음 |
| 상품·공식 순위 | 현재는 Google 시트의 관찰/승인 → 생성된 게시 스냅샷 | 시트 원본은 운영 전용, 앱은 승인된 버전만 읽기 | 매장 DB와 분리. 상품번호는 안정 식별자, 순위·화면 가격은 관찰 시각을 가진 스냅샷 |
| 미디어 | 파일 저장소 + 신규 `media_assets`, `place_media` 메타데이터 | 미승인/권리 증빙은 비공개, 게시 승인 이미지 경로만 공개 | DB에 이미지 바이너리 저장하지 않음. 파일 교체는 버전 경로로 수행 |
| 스토리 | 별도 블로그의 게시물이 원본; 앱은 `story_publications` 투영 | 공개 승인된 버전만 비회원 조회; 앱에서 본문 역수정 없음 | `source_id`, `canonical_url`, `published_at`, `source_updated_at`, `synced_at`으로 중복·지연 관리 |
| 피드백·이용 측정 | 기존 `feedback` + 별도 최소 이벤트 계약 | 피드백 원문은 운영 담당만; 이벤트는 원칙적으로 집계·최소 수집 | 가입 수를 활성 사용자 수로 오인하지 않음. 위치 원좌표·민감 검색어는 기본 수집하지 않음 |

### 3.1 장소와 ID

`places`의 최소 공개 필드는 `id`, `type`, 한글/영문 이름, 주소, 좌표, 지역, 공개 상태, 영업 상태, `updated_at`이다. 영업시간·면세·유심·가격·언어 지원처럼 변동성 있는 속성은 값마다 출처와 확인일을 연결한다. `place_source_records`는 공식 매장찾기·오너 제공 자료 등 수집 단위의 출처 URL/식별자·관찰 시각·원본 해시를 보관한다. `place_field_evidence`는 특정 장소·필드의 현재 게시값이 어떤 원천·검수 결과에서 왔는지 연결한다. `place_revisions`는 승인 전후의 변경과 되돌리기 근거를 남긴다.

매장 폐점·이전 시 기존 `id`는 재사용하지 않는다. 공식 `store_code`가 있으면 소스와 함께 대조하지만 내부 ID를 공식 코드로 일괄 교체하지 않는다. 현재 `favorites`·`ratings`의 장소 ID 길이 제약과 실제 생성 ID를 먼저 대조한다. 카탈로그에 FK를 추가하는 일은 기존 찜·리뷰의 모든 ID가 보존/매핑됨을 확인한 뒤 별도 변경으로 다룬다.

`publication_state`(`draft`/`published`/`hidden`)와 `business_state`(`open`/`temporarily_closed`/`closed`/`unknown`)는 별개다. 원천이 새 매장을 보여도 승인 전에는 공개되지 않는다. 일시적 수집 실패를 폐점으로 해석하지 않는다. 필수 근거가 오래되면 운영 검수 대상으로 표시하고, 근거가 없는 `LIVE`·실시간 표현은 하지 않는다.

초기 테이블 배치는 아래와 같다. `internal`은 Data API 비노출 스키마로 두고, `public`의 신규 테이블은 필요한 역할에만 명시적으로 권한을 준다. 실제 SQL·인덱스는 운영 DB 제약 확인 후 A/B 프로젝트별 마이그레이션에서 확정한다.

| 테이블 | 핵심 키·필드 | 제약·조회 방식 |
|---|---|---|
| `public.places` | `id text` PK, 유형, 이름·주소·좌표, `publication_state`, `business_state`, 수정/확인 시각 | 기존 ID 그대로. 비회원은 게시 행만 읽고 직접 수정 불가. 이름/지역 검색과 지도 범위 조회에 필요한 인덱스는 실제 쿼리로 결정 |
| `public.place_hours` | `place_id`, 요일·예외 날짜, 영업/휴무 구간, 확인 시각 | 확인된 요일만 게시. 하루 관찰값을 7일 공통 영업시간으로 복제하지 않음 |
| `public.place_features` | `place_id`, 시설·서비스 코드, 확인 시각 | 면세·유심·픽업 등을 장소별 사실로 저장. 확인되지 않은 태그는 표시하지 않음 |
| `public.place_services` | `place_id`, 서비스명, 소요시간·표시 가격, 가격 확인 시각 | 검증된 샵 메뉴만 기록. 빈 매장에는 데모 메뉴를 채우지 않음 |
| `internal.place_source_records` | UUID PK, `place_id`, 원천 종류/외부 매장 코드/URL, `observed_at`, 원본 해시·비공개 원본 경로 | 원천 한 번의 관찰을 불변 기록으로 저장. 수집 실패나 0건 응답은 게시 삭제 명령이 아님 |
| `internal.place_field_evidence` | UUID PK, `place_id`, 필드명, `source_record_id`, 확인 시각/담당 | 게시된 변동 필드가 어떤 관찰에 근거하는지 추적. 참조 키는 인덱스 대상 |
| `internal.place_revisions` | UUID PK, `place_id`, 변경 전후 스냅샷, 승인자·게시 시각 | 승인/롤백 감사 기록. 앱은 이 테이블을 직접 조회하지 않음 |
| `internal.media_assets` | UUID PK, 저장 경로, 체크섬, 형식·크기, 권리 상태·승인 상태 | 권리 증빙과 미승인 원본은 비공개. 바이너리는 Storage에 보관 |
| `public.place_media` | `place_id`+`asset_id`, 공개 경로, 정렬 순서·대표 여부 | 승인된 파일만 게시 연결. 파일 교체 시 새 버전 경로를 가리킴 |
| `internal.external_rating_snapshots` | 장소 ID, 플랫폼, 점수·건수, 관찰 시각, 허용 근거 | 수집·표시 권리가 검증된 데이터만 공개 투영; 자체 리뷰 집계와 별도 |
| `public.story_publications` | 원본 시스템+외부 ID, slug, canonical URL, 제목·요약·정화된 본문, 게시/수정/동기화 시각, 공개 상태 | 승인 글만 읽기. 동일 원본의 재동기화는 새 중복 글을 만들지 않음 |

이 배치는 앱의 런타임 조회 모델과 내부 검수 이력을 분리하려는 안이다. `public`이라는 스키마 이름만으로 공개를 뜻하지 않는다. 각 객체의 실제 Data API 노출, `GRANT`, RLS와 뷰의 실행 권한을 별도 확인한다.

### 3.2 회원·리뷰·댓글

`profiles`는 당장 별도 물리 DB로 옮기지 않는다. 민감도가 다른 신규 연락처·예약 관련 데이터가 생기면 별도 비공개 테이블과 목적별 권한을 설계한다. 계정 이메일·비밀번호 해시를 앱 프로필에 중복 저장하지 않는다. 별도 DB는 수집 목적·접근 담당·복구 경계가 실제로 달라질 때 검토한다. 물리적 분리만으로 암호화가 되는 것은 아니다.

자체 리뷰는 현재 회원당 장소 한 건 정책을 유지한다. 비회원은 별점/비공개 초안을 기기에 저장할 수 있으나, 다른 사람에게 보이는 글을 게시할 때만 로그인과 명시적 공개 선택이 필요하다. 운영자 `hidden`과 신고 처리 상태는 작성자가 변경할 수 없게 컬럼 권한/서버 경로를 검증한다. `public_reviews`는 공개에 필요한 `id`, 장소, 평점, 본문, 공개 표시 이름, 게시 시각만 제공하며 계정 이메일·원본 사용자 ID·내부 신고 상태를 노출하지 않는다. 표시 이름은 사용자가 승인한 별칭 또는 안전한 기본값으로 옮기고, 인증/관리자 권한 판단에는 사용자 수정 가능한 메타데이터를 쓰지 않는다.

댓글은 **지금 만들지 않는다**. 리뷰 흐름과 운영 신고 처리가 안정되면 `review_comments(review_id, author_id, body, state, created_at, updated_at)`를 별도 테이블로 추가한다. 같은 DB 안의 분리로 충분하며, 별도 DB는 필요하지 않다. 공개 전 길이·링크/스팸·금칙 표현 검사를 하되 문자열 차단만으로 안전하다고 보지 않는다. 신고, 숨김, 이의 제기, 반복 남용 제재와 운영자 복원 경로가 준비되어야 출시한다.

### 3.3 이미지와 스토리

이미지는 디자이너가 수동 제작한 결과물을 게시 승인한다. `media_assets`에는 원본/가공본의 저장 경로, MIME, 크기, 체크섬, 저작권/사용 허락 근거, 제작·승인자, 생성·승인 시각, 공개 상태를 둔다. `place_media`는 장소·이미지·정렬 순서·대표 이미지 여부를 연결한다. 미승인 원본과 권리 증빙은 비공개 저장소, 게시 승인 파일만 공개 URL로 제공한다. 현재 저장소의 `public/places`와 `public/brands`는 즉시 이동하지 않고, 사용 권리와 경로를 조사한 뒤 단계적으로 이전한다. 공식 매장 사진을 사용할 권리는 공식 정보 출처 여부와 별개로 확인한다.

스토리는 별도 블로그의 발행 시스템을 유일한 편집 원본으로 한다. 최초 연결에서는 플랫폼별 수집기를 직접 결정하지 않고 다음 계약만 고정한다: `source_id`와 canonical URL로 멱등 매칭, `published`만 반영, 수정/발행 취소 반영, HTML/임베드 정화, 이미지 사용 권리 검사, 실패 시 기존 승인 버전 유지 및 운영 알림. 앱의 글 목록과 상세는 같은 승인된 버전을 읽어 제목·본문 불일치를 막는다. 블로그 플랫폼·URL·API/피드·권한 확인 전에는 자동 동기화나 새 CMS 설치를 하지 않는다. 그 전 단계의 임시 개선은 잘못된 앱 상세 본문을 게시된 원문 링크로 연결하거나 명확히 숨기는 별도 승인 작업이다.

### 3.4 상품·순위는 장소 DB와 분리

상품 추천은 보조 기능이므로 첫 100명 단계에서 순위 원천 전체를 장소 DB에 옮기지 않는다. 현재 합의한 경로는 **공식몰 관찰 → Google 시트 → 차트별 검증/게시 승인 → 버전이 있는 앱 스냅샷**이다. 실패하면 마지막 정상 게시본을 유지한다. 이 경로는 아직 운영 자동 갱신 완료 상태가 아니다.

상품의 안정 식별자는 `판매처 + 공식 상품번호`다. 순위는 판매처·카테고리·차트·관찰 시각·원순위의 조합이고, 가격은 그 시점 화면의 표시값이다. 상품 상세/저장 링크에 쓰는 누적 상품 원장과 현재 TOP20 게시 목록은 분리한다. 순위에서 빠진 상품의 상세 페이지를 삭제하지 않는다. 올리브영의 카테고리별 1위를 임의의 전체 1위로 합치지 않고, 자체 Review Best는 회원 상품 리뷰가 실제로 생기기 전까지 별도 준비 상태로 둔다. 공식 순위의 세트·옵션 행과 `단품만 추천` 심사는 다른 결정이다.

향후 순위 이력 검색, 운영 분석, 리뷰 기반 상품 기능이 실제로 필요해지면 그때 `products`, `ranking_runs`, `ranking_rows` 같은 DB 테이블로 옮길지 판단한다. 그 경우에도 기존 Google 시트/게시 스냅샷과 이중 원본을 만들지 않고 한 경로만 원본으로 지정한다. 자동 이미지 수집은 이 순위 흐름에 포함하지 않는다.

## 4. 접근 권한과 데이터 흐름

|---|---|---|---|
| 게시 장소·승인 이미지·게시 스토리 읽기 | 허용 | 허용 | 허용 |

| 초안 장소·원천 증빙·미승인 이미지 읽기 | 거부 | 거부 | 업무별 최소 권한 |
| 프로필·찜·자신의 비공개 별점 읽기/수정 | 기기 내 자료만 | 자기 행만 | 원문 접근은 필요성·기록에 따라 제한 |

공개 클라이언트에는 Supabase 공개용 키만 둔다. `service_role`/secret은 서버의 제한된 경로에서만 사용하며, 사용자 요청을 받는 경로는 먼저 세션·대상 ID·행위 권한을 확인한다. 노출된 테이블/뷰에는 역할별 `GRANT`와 RLS를 모두 검증한다. 내부 테이블은 Data API에 노출하지 않는 스키마 또는 서버 전용 경로로 둔다. 권한 검사에 `user_metadata`를 쓰지 않는다. 공개 뷰와 `SECURITY DEFINER` 함수는 역할별 테스트와 별도 코드 리뷰를 거친다.

운영자는 공유 계정 대신 개인별 관리자 계정을 사용한다. 디자이너는 이미지 업로드/검수 요청, 콘텐츠 담당은 장소·스토리 초안, 프런트 개발자는 배포/스키마 변경, 마케팅 담당은 집계 보고서만 보는 구분을 기본으로 한다. 실제 관리 화면 또는 대시보드 권한은 도입 시 별도 검증하며, 현재 권한이 이렇게 설정됐다고 가정하지 않는다.

## 5. 갱신·장애·복구 흐름

장소 변경은 **수집 → 차이 확인 → 원천/권리 검수 → 승인 → 게시 → 앱 확인**으로 처리한다. 공식 목록 수집이 실패하거나 행 수가 급감하면 이전 게시본을 유지하고 알림을 남긴다. 가격·영업시간·외부 평점처럼 변동이 빠른 값은 마지막 확인일을 표시하거나 확인 전 숨긴다. 리뷰 신고는 접수·숨김·복원 이력을 남긴다. 스토리 수집 실패 시 이전 게시본 유지, 발행 취소는 다음 검수/동기화에서 앱에도 반영한다.

DB 백업과 이미지 파일 백업은 별개다. 첫 100명 단계의 운영 목표는 DB와 게시 미디어의 일일 복구 가능 사본, 분기별 복원 연습, 권한·키 회수 절차다. 실제 백업 제공 범위와 복구 소요는 현재 요금제·프로젝트 설정을 확인해 기록한다. DB 백업만으로 Storage 파일까지 복원됐다고 판정하지 않는다.

## 6. 단계별 이전과 검증 기준

### A. 회원·커뮤니티 안전성 — 먼저 실행할 독립 프로젝트

1. 운영 Supabase의 실제 테이블, 마이그레이션 이력, `GRANT`/RLS/뷰/함수, 백업 상태를 **읽기 전용**으로 대조한다. 현재 로컬 코드의 정책을 운영 적용 완료로 표시하지 않는다.
2. 익명·회원 A·회원 B·운영 역할로 프로필, 찜, 공유목록, 비공개/공개 리뷰, 신고, `hidden` 변경을 검증한다. 공개 뷰의 계정 정보 노출도 확인한다. 실패가 확인된 권한만 작은 마이그레이션으로 수정한다.
3. 계정 내보내기의 포함 범위(프로필·찜·별점/리뷰·공유목록·계정 연결 피드백/신고)를 정의하고, 조회 실패를 빈 자료로 바꾸지 않는다. 계정 삭제 시 FK cascade·스토리지·추가 데이터의 처리를 실제 데이터로 검증한다.
4. 비회원 핵심 동선을 유지하면서 공개 리뷰에만 로그인 요구하는 회귀 테스트를 통과시킨다. 운영 적용은 백업·사전배포·롤백 경로를 확인한 뒤 별도 승인으로 진행한다.

완료 판정: 타인 비공개 행·목록 나열·관리 필드 수정이 거부되고, 본인 데이터 내보내기/삭제가 정의된 범위와 일치하며, 비회원 지도·검색·길찾기가 유지된다. 테스트 통과와 운영 검증을 별도 상태로 기록한다.

### B. 장소·미디어 카탈로그 — A와 별도 릴리스

1. 기존 공개 장소 전체를 ID·URL·찜·리뷰 참조와 함께 추출한다. 공식 매장 코드와 필드별 출처, 폐점·중복·가상 샘플을 분리한다.
2. 신규 카탈로그에 초안으로 이관하고 `lib/data.ts` 생성 결과와 **ID·건수·필수 필드·지도 좌표·대표 이미지 경로**를 비교한다. 차이가 있으면 공개 스위치를 하지 않는다.
3. 앱 조회를 카탈로그로 전환하되 문제 시 마지막 검증된 스냅샷으로 되돌릴 수 있게 한다. 정적 파일 삭제, DB FK 추가, 이미지 파일 이동은 각각 별도 단계다.
4. 공식 목록 갱신은 수집 성공 여부와 차이 검수 결과를 기록한다. 검수되지 않은 원천 행이 자동으로 게시되거나 폐점 처리되지 않게 한다.

완료 판정: 기존 저장 링크·별점·공유목록이 같은 장소를 가리키고, 비회원 지도/상세가 현재 승인 데이터와 일치하며, 초안·미승인 사진은 외부에서 읽히지 않는다.

### C. 스토리 연결 — 블로그 시스템 식별 후 별도 릴리스

1. 오너가 별도 블로그의 URL, 관리 플랫폼, 발행 권한, API/RSS/내보내기 방식과 이미지 재사용 권한을 확인한다.
2. 발행·수정·취소·동일 slug·동기화 실패의 계약 테스트를 만든다. 앱 목록/상세의 동일 버전과 canonical URL을 확인한다.
3. 잘못된 기존 공통 본문을 제거한 뒤 승인된 글부터 앱에 반영한다. 새 CMS를 이중 편집 공간으로 만들지 않는다.

완료 판정: 블로그에서 승인한 게시·수정·취소가 앱에 예측 가능한 시간 안에 일치하고, 실패 시 잘못된 새 글이 아니라 마지막 승인본 또는 명확한 비공개 상태가 보인다. 동기화 주기는 원본 플랫폼의 기능과 편집 담당자의 운영 시간을 확인한 뒤 C 설계에서 확정한다.

### D. 상품 랭킹 — 별도 운영 트랙 유지

랭킹은 이미 준비된 Google 시트와 게시 스냅샷 경로를 사용한다. 최초 실운영 게시, 정기 갱신, 실패/이전 정상본 유지 검증은 `reports/operations/ranking-google-sheet-operations-2026-09-26.md`의 승인 게이트를 따른다. 장소 카탈로그 DB 전환 때문에 랭킹 경로를 변경하지 않는다. 랭킹 게시가 나중에 재개될 때에도 상품번호·상세 링크·관찰일과 차트별 원순위를 대조한다.

## 7. 이용 측정과 운영 확장 기준

회원 수만으로 사용 여부를 판단하지 않는다. 장소 검색→상세→저장→길찾기, 리뷰 공개 전환, 가입 시도/성공의 **각 분모와 성공 사건**을 정의한다. 비회원은 계정 ID와 연결하지 않는 짧은 수명의 세션 식별자를 우선 검토하고, 정밀 GPS·건강 관련 입력·검색어 원문은 기본 수집하지 않는다. 이벤트 수집 목적·동의/고지·보유 기간·내부/봇 제외 방식이 정해지기 전에는 개인 행동 추적을 출시하지 않는다. 현재 `web_vitals`를 방문자 수나 재방문율로 해석하지 않는다.

100명이 넘는다는 이유만으로 DB를 분리하지 않는다. 실제 분리 검토 신호는 법적/계약상 격리 의무, 독립 운영팀과 접근 경계, 복구 목표의 충돌, 측정된 성능/비용 병목이다. 먼저 읽기 성능·인덱스·캐시·배치와 운영 권한을 조정하고, 물리 분리는 명확한 장애·보안 이득이 있을 때 설계한다.

## 8. 문서 검토 후 필요한 결정

이 설계의 A 운영 상태 확인과 B의 로컬 카탈로그 설계는 별도 블로그 정보 없이 착수 가능하다. B의 이미지 게시와 C의 연동을 운영에 반영하기 전에 아래 입력을 확보한다.

- **B:** 사진 사용 허락 범위, 장소 필드별 검수 담당자, 공식 매장 원본의 운영 인수인계 경로.
- **C:** 별도 블로그의 실제 URL·플랫폼·게시 인터페이스·이미지 권리.
- **D:** 공식 순위 시트의 운영 게시 재개 여부와 담당자. 기존 1회 시험 행은 정식 게시본으로 승격하지 않는다.
- **공통:** 개인정보/이벤트 보유 기간과 지원 문의 담당·회신 채널은 오너/법률 검토 후 운영 정책으로 확정한다. 이 확인 전에는 새 개인정보 수집이나 자동 게시를 시작하지 않는다.
