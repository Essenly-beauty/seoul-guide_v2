# MYSEOULDROP 웹앱 운영 준비 검토

검토일: 2026-09-23, 한국 시간. 대상: `https://myseouldrop.app`, 현재 저장소, 연결된 Supabase의 제한적 읽기 점검, GitHub Actions 실행 기록.

## 1. 결론

**탐색형 웹앱의 기본 기능은 동작하지만, 현재 상태로 정식 공개 운영을 승인하기는 어렵다.** 가장 먼저 해결할 것은 공유목록 접근 권한이다. 다음으로 실제 데이터처럼 표시되는 샘플 콘텐츠, 위치·영업시간의 신뢰성, 운영자 연락처와 개인정보 안내, 계정 복구·백업 체계를 정리해야 한다.

처음부터 예약·결제 플랫폼을 만들 필요는 없다. 현재 구현에 맞는 첫 출시 범위는 ‘외국인 여행자를 위한 장소 탐색 → 상세 확인 → 저장 → 외부 길찾기’다. 공개 리뷰·공유·랭킹은 각각의 운영 조건을 충족한 뒤 포함하는 것이 현실적이다. 이는 제안이며, 사업 범위는 운영자의 답변으로 확정해야 한다.

이 보고서는 **1차 운영 실사**다. 법률 적합성 인증, 침투 테스트, 모든 단말에 대한 QA, 관리자 콘솔 설정의 전수 검증을 완료했다는 의미는 아니다. 앱 코드·DB 정책·배포는 수정하지 않았다.

## 3. 발견 사항과 완료 기준

### OPS-01. 공유목록의 ‘링크를 가진 사람만’이라는 전제가 성립하지 않음 [P0]

- 근거: `supabase/migrations/0006_shared_lists.sql:17` 이후 익명 SELECT 정책이 `using (true)`. UUID가 추측하기 어렵더라도 테이블 목록 조회가 열리면 링크 비밀성이 보장되지 않는다.
- 운영 확인: 익명 요청으로 ID 조건 없이 `shared_lists`의 `id,owner` 선택과 정확한 개수 조회가 허용됐다. 응답은 `206`, 전체 개수 1이었다. `limit=0`으로 내용·소유자 식별자 자체는 가져오지 않았다.
- 영향: 링크를 받지 않은 사람이 공유 목록을 발견할 수 있는 접근 제어 문제. 실제 제3자 열람이나 개인정보 유출 사건이 있었다는 증거는 확인하지 않았다.
- 필요한 조치: 익명 테이블 나열 금지, 정확한 공유 토큰을 검증하는 제한된 조회 경로, 소유자 ID 비노출, 공유 중단/재발급, 계정 삭제 시 정리. UI만 숨기는 것은 해결이 아니다.
- 완료 기준: 익명 전체 조회 실패, 토큰 없는/잘못된 요청 실패, 유효 링크의 필요한 필드만 반환, 폐기 링크 실패, 다른 회원의 목록 관리 실패를 자동 테스트. 기존 공유 1건의 처리도 운영자가 결정.

### OPS-02. 실제 판매·리뷰 랭킹으로 오인할 수 있는 고정 콘텐츠 [P1]

- 근거: `lib/data.ts:523`의 고정 14개 상품과 `salesRank/reviewRank`를 `lib/ranking.ts`가 사용. `components/ranking/ranking-page-client.tsx:258`은 이를 `Today's sales ranking` 또는 `Highest-rated by reviews`로 표시. 운영 화면에서도 확인했다.
- 다이소는 별도 데이터이며 수집 기준일은 **2026-08-31**이다. 올리브영 샘플과 같은 문제로 묶어 ‘전부 가짜’라고 해석하면 안 된다. 다만 현재성 고지와 갱신 담당자는 필요하다.
- 완료 기준: 실제 출처·수집일·대상 범위·정렬 기준·갱신 실패 시 동작 표시. 판매량/리뷰 데이터가 없다면 편집 추천으로 명칭 변경하거나 출시에서 제외. 매장 상세의 ‘chain-wide bestsellers’에도 동일 원칙 적용.

### OPS-03. 기사 내용과 약속이 실제 기능과 맞지 않음 [P1]

- 재현: `/blog/seoul-beauty-hotspots-hongdae`를 열면 홍대·신사 가이드 제목 아래 공통 스킨케어 루틴 본문이 나온다.
- 근거: `app/blog/[slug]/page.tsx:34` 이후 본문이 모든 기사에 공통. 하단은 무료 hair kit를 약속하고, Sign Up은 가입 화면이 아닌 `/`로 연결한다. 공유 문자열의 도메인도 `myseouldrop.com`으로 정식 `.app`과 다르다.
- 완료 기준: 기사별 검수 본문·출처·작성/수정일, 실제 이행할 수 있는 제안만 사용, 정확한 CTA와 도메인. 준비 안 된 콘텐츠는 비노출 가능.

### OPS-04. 임시 좌표가 정밀 거리로 표시됨 [P1]

- 재현: 검색에서 Myeongdong → 명동역 지도 → 역 주변 목록. `Lotte Outlets Seoul Station`이 `20 m from the station`으로 표시됐다. 해당 목록 행에는 임시 위치 설명이 없었다.
- 근거: `lib/generated/ados-photo-provisional-places.ts:994`의 해당 장소는 `geoSource: area`, `locationVerification: provisional`. `components/subway/subway-route-controller.tsx:950`은 계산 거리를 출력한다. 다른 선택 요약에는 Approximate pin이 있어도 이 거리 표시를 충분히 설명하지 못한다.
- 완료 기준: 정확 위치를 검증한 장소만 정밀 거리·역 반경 추천에 사용하거나, 모든 관련 화면에서 근사값임을 명확히 표시. 임시 좌표를 실제 출입구로 안내하지 않기. 우선 방문 수요가 높은 지역부터 주소·좌표·폐업·중복 검수.
- 108개를 모두 오류라고 단정하지 않는다. 문제는 확인 수준보다 정밀하게 보이는 안내다.
- 검토 중 다른 작업이 추가한 `data/sources/oliveyoung-seoul-2026-09-23.json`도 별도로 대조했다. 해당 로컬 공식 사이트 수집 스냅샷 366개와 앱 236개의 지점명을 정규화해 비교하면 스냅샷에만 138개, 앱에만 8개가 있다. **누락·개명·이전·폐점 검수 큐**로 사용해야 하며, 이름 불일치 8개를 확인 없이 폐점 처리하면 안 된다. 이 숫자는 로컬 스냅샷 비교이지 공식 사이트 전수 재수집 결과는 아니다.
- 함께 추가된 `docs/research/store-data-accuracy-2026-09-23.md`의 ‘앱 올리브영 사진 0장’은 현재 합성 데이터와 맞지 않는다. 최종 `PLACES`에서는 올리브영 225곳에 사진 필드가 있고 운영 학동중앙점 화면에서도 사진을 확인했다. 원본 수집 파일만 보고 최종 화면의 사진 유무를 판단하지 않도록 주의한다.

### OPS-05. 서울 매장의 영업 상태를 방문자의 현지 시간대로 계산 [P1]

- 근거: `lib/places.ts:34`와 `:53`의 `getDay/getHours/getMinutes`가 기기 현지 시간 사용.
- 재현: 같은 순간 `2026-09-23T03:00:00Z`, 매장 영업시간 10:00~20:00. Asia/Seoul에서는 open, America/New_York에서는 closed. 위 증거 수집 스크립트로 재현했다.
- 완료 기준: 서울 매장은 Asia/Seoul 기준으로 요일·시간 계산. 해외 여행 준비 중인 사용자와 서울 방문 사용자의 결과 동일. 자정 경계, 휴일·휴무, 미확인 시간, 익일 종료 시간도 별도 테스트.

### OPS-06. 초안 법적 안내와 답변 불가능한 문의 구조 [P1]

- 운영 개인정보 화면에 `Draft for review` 표시. 운영 법인/개인사업자명, 책임자·실제 연락처 확정이 필요하다.
- Support는 도메인이 이미 있는데도 ‘도메인과 함께 직접 이메일이 준비된다’고 안내. 피드백 양식은 종류·본문만 받으며 `components/ui/feedback-sheet.tsx:30`은 `contactOk: false`로 고정되어 있다.
- 따라서 단순 제보 수집은 가능해도, 이용자가 답변을 받을 지원 창구라고 보기 어렵다. 마케팅 철회·개인정보 요청을 Support로 하라는 정책과 특히 맞지 않는다.
- 개인정보 문서에는 Supabase/Vercel/Google이 있지만 실제 지도 요청을 받는 CARTO 검토가 빠져 있다. 진단 데이터 12개월 삭제 약속은 저장소에서 정기 삭제 구현을 확인하지 못했다. DB 예약 작업은 별도 확인 필요.
- 완료 기준: 운영 주체, 지원·개인정보 연락처, 수집 항목/목적/보존/삭제, 실제 국외 처리 현황과 근거, 권리 행사, 미성년 이용 방침을 확정하고 실제 시스템과 일치. 피드백·진단·백업 각각의 보존 정책과 담당자 지정.
- 한국 개인정보 처리방침과 국외 이전은 구체적인 법적 요건을 확인해야 한다. 이 보고서는 법률 자문이 아니며 운영자 사실관계 확정 후 전문가 검토가 필요하다. [개인정보 보호법 제30조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1029331583), [제28조의8](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029334953)
- ‘해외 방문자라서 무조건 쿠키 배너 필요/불필요’로 결정하지 않는다. 실제 저장 기술, 대상 시장, 광고·분석 도입에 맞춰 검토한다. CARTO 요청의 기술 정보 처리도 반영해야 한다. [CARTO Basemap Terms](https://carto.com/legal/basemap-terms/)

### OPS-07. 계정 메일과 복구 경로의 운영 검증 미완료 [P1]

- 운영 Auth 설정에서 이메일 가입 자동 확인(`mailer_autoconfirm`)이 true임을 확인했다. 이것만으로 곧바로 잘못된 설정이라고 단정하지 않는다.
- 가입 확인을 끄더라도 비밀번호 재설정·이메일 변경은 메일 전달이 필요하다. 기존 문서에는 SMTP 미설정 기록이 있지만 현재 관리자 콘솔에서는 재확인하지 못했다.
- Supabase 기본 SMTP는 팀에 등록된 주소 중심의 제한된 테스트용 서비스이며 일반 공개 운영용으로 보장되지 않는다. 커스텀 SMTP 설정 여부, 발신 도메인 검증, 발송 한도·차단·반송 처리가 필요하다. [Supabase SMTP 공식 안내](https://supabase.com/docs/guides/auth/auth-smtp)
- 완료 기준: 승인된 테스트 계정으로 외부 메일 수신, 스팸함, 재설정 링크 단일 사용/만료, Google 로그인, 로그아웃, 다른 기기 동기화, 기존 로컬 저장 병합, 계정 삭제까지 확인. 인증 실패 경보와 지원 절차 포함.
- 가입 동의 버전·시각과 마케팅 철회 이력을 관리해야 한다. 현재 이메일 가입의 user metadata만으로 영구적인 감사 이력이라고 보기는 어렵고 Google 흐름은 별도 점검이 필요하다. 서버 비밀번호 최소 길이 강화는 기존 보류 결정이 있으므로 자동으로 정책을 바꾸지 않는다.

### OPS-08. 보안 업데이트와 권한·남용 방어 [P1]

- `npm audit`에서 next/sharp/postcss/nanoid 관련 영향 노드가 발견됐다. 설치 Next.js는 15.5.23. AVIF 이미지 최적화 관련 공식 권고는 15.5.24 등에 패치가 있다고 안내한다. 무조건 메이저 버전 이전보다 현재 버전대의 안전한 패치를 우선 검토할 수 있다. [Next.js 보안 권고](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4)
- Windows 한정 권고도 있으므로 npm severity를 그대로 ‘Vercel에서 원격 실행 가능’으로 번역하면 안 된다. 이번 검토에서는 실제 공격 가능성을 입증하지 않았다. [Windows 조건의 권고](https://github.com/advisories/GHSA-p293-qw3h-jr36)
- 리뷰: `0003_ratings.sql:27`은 소유자 행 업데이트를 허용하고, `0007_public_reviews.sql:18`이 `hidden`을 추가한다. 저장소에서는 이 관리용 필드에 대한 사용자 수정 금지를 확인하지 못했다. 숨김 해제 우회 가능성을 운영 DB 컬럼 권한과 테스트 계정으로 확인해야 한다. 운영 데이터에 대한 우회 시도는 하지 않았다.
- 피드백·오류·성능 테이블은 익명 쓰기가 가능하다. 클라이언트 횟수 제한 또는 앱의 API 제한만으로 Supabase 직접 호출까지 보호되지는 않는다. DB/인증/서버 경로를 함께 설계해야 한다.
- 완료 기준: 익명·회원 A·회원 B·관리자 권한 행렬 테스트, 검토 필드 보호, 쓰기 크기/횟수 제한, 스팸 격리, 사용자 차단·이의제기. 관리자 계정 MFA, 최소 권한, 키 보관·회수, 로그 민감정보 제거도 확인.
- 긍정 확인: 기본 개인 테이블들은 익명 읽기에서 노출 건수 0이었다. 이는 회원 간 격리 전체를 검증했다는 뜻은 아니다. 공개 리뷰 view는 공개 동의한 필드를 노출하도록 의도된 구조이므로 definer라는 이유만으로 결함으로 분류하지 않았다.

### OPS-09. 개인정보 내보내기의 누락과 실패 처리 [P1]

- 근거: `app/api/account/export/route.ts:11`은 프로필·즐겨찾기·평점만 조회. 공유목록·동의 정보 등 다른 관련 데이터의 포함 범위가 불명확하다.
- 각 조회 실패를 구별하지 않고 빈 배열/null로 대체해 정상 다운로드처럼 반환할 수 있다.
- 완료 기준: ‘내 데이터’의 정확한 범위 정의, 관련 데이터와 공개 여부 포함, 일부 조회 실패 시 명확한 실패/부분 성공 안내, 본인 인증·타 사용자 격리, 다운로드 캐시 방지 검증. 계정 삭제는 연결 데이터·공유·백업 보존까지 설명 일치.

### OPS-10. 배포·모니터링·운영 문서의 연결이 약함 [P1]

- 코드 검증 시 로컬 HEAD는 `79e0da1`, origin/main보다 6개 커밋 앞서 있었다. 이후 별도 작업의 자료·문서 커밋 `83731a6`이 추가돼 7개 앞선 상태를 확인했다. 해당 추가 커밋은 앱 구현을 바꾸지 않았다. 최신 운영 성능 이벤트의 release 값은 `75868234c745`다. 로컬 성공을 최신 운영 배포 성공으로 취급하지 않았다. 배포 SHA는 Vercel 콘솔에서도 최종 대조가 필요하다.
- CI에는 타입/린트/테스트/빌드가 있으나 데이터 감사·의존성 보안 점검·핵심 E2E를 출시 승인 조건으로 연결하지 않았다.
- `.github/workflows/uptime.yml`은 정식 `.app`이 아닌 Vercel 기본 주소를 검사하며 모든 HTTP probe에서 401/403을 성공 처리한다. export의 예상 401과 지도 페이지의 403은 구분해야 한다.
- 예약 visitor smoke는 6개 탐색 테스트가 중심이고 계정 데이터 테스트는 수동 선택 시만 실행. 랭킹·메일·삭제가 정상이라는 증거로 확대 해석하면 안 된다.
- 완료 기준: 정식 도메인 DNS/TLS/HTML·지도·Auth·핵심 DB·메일을 계층별로 감시. 경보 수신자, 확인 기한, 백업 담당자, 롤백 방법을 지정. 빌드 SHA/환경/마이그레이션을 한 릴리스 기록으로 묶기.
- 예전 프로토타입 문서와 최근 HANDOFF의 설명이 다르므로 운영용 기준 문서 하나를 지정하고 ‘확인일·담당자·증거’를 기록해야 한다.

## 4. 실제 운영에 필요한 체계

### 4.1 사업 범위와 책임

출시 전에 다음을 한 장으로 확정해야 한다.

1. 누구를 돕는가: 방한 전 여행 준비자 / 서울 체류 관광객 / 장기 거주자, 우선 언어와 국가.
2. 핵심 약속: 가까운 장소 발견인지, 영어 응대 검증인지, 상품 추천인지. 검증되지 않은 약속은 하지 않는다.
3. 첫 출시 기능: 무료 탐색·저장·외부 길찾기 / 공개 리뷰·공유 / 광고·제휴 / 예약·결제 중 어디까지인지.
4. 운영 주체: 계약과 개인정보 처리의 주체, 도메인·코드·데이터·계정 소유자, 대체 담당자.
5. 수익 구조: 제휴 링크·유료 노출·상품 판매를 도입한다면 광고 표시와 추천 순위 독립성, 매장과의 관계를 설명.

예약·결제를 추가하면 결제 성공 화면뿐 아니라 취소·환불·노쇼·분쟁·정산·판매자 확인·세무·고객지원까지 별도 범위다. 의료기관·시술 알선 또는 건강 정보 수집을 포함할 경우에도 별도 법률·개인정보 검토가 필요하다. 현재 탐색 앱이 이 운영 준비를 갖췄다고 가정하지 않는다.

### 4.2 장소·상품·콘텐츠 운영

| 대상 | 최소 관리 항목 | 권장 운영 규칙 |
|---|---|---|
| 장소 | 원천 출처, 주소·좌표, 지점 ID, 영업/휴폐업, 마지막 확인일, 검수자 | 수요 높은 지역·장소 우선 검수. 제보가 들어오면 재확인까지 위험한 안내 제한 |
| 영어 응대 | 확인 근거, 범위, 확인일 | 일부 직원/예약 채널의 영어 가능과 상시 영어 응대를 구분 |
| 영업시간·가격 | 기준일, 휴무/공휴일 예외, 가격 조건 | 정보 없음은 없음으로 표시. 확인되지 않은 기본값을 사실처럼 채우지 않음 |
| 평점·리뷰 | 출처, 표본 수, 집계 시각, 자체 리뷰 여부 | 외부 평점과 MYSEOULDROP 방문 후기를 구분 |
| 랭킹 | 수집 권한, 기준 시각, 집계 범위, 정렬 방식 | 최신 수집 실패 시 ‘오늘’ 표시 중단, 이전 기준일 표시 |
| 사진·설명 | 소유자/라이선스, 허락 증빙, 허용 채널·기간, 삭제 요청 이력 | 기존 허락 기록을 파일별 원장과 연결. 재수집 데이터는 별도 확인 |
| 기사 | 제목별 본문, 출처, 검수, 수정일, 실제 가능한 CTA | 운영자가 관리 가능한 발행 빈도부터 시작 |

`audit:data:check`를 통과시키되, 보고서 날짜만 갱신해 통과하는 것과 실제 데이터 검수는 구분해야 한다. 미확인 데이터는 별도 큐로 관리하고 사용자 화면에서 그 한계를 알려야 한다. 초기에는 검증된 핵심 지역을 좁혀 운영하는 선택도 가능하다.

### 4.3 고객지원·리뷰 운영

- 실제 수신 가능한 지원 메일/창구, 한국 시간 기준 운영 시간, 지원 언어, 1차 회신 목표를 공개한다. 예: 영업일 1일 내 1차 회신은 **제안 목표**이며 운영자의 인력 확인 후 확정한다.
- 문의에 접수 ID, 분류, 담당자, 상태, 생성/처리 시각, 답변 기록을 남긴다. 초기에 복잡한 관리자 앱이 필수는 아니지만 누가 언제 처리할지는 정해져야 한다.
- 잘못된 위치·폐업·계정 접근 불가·개인정보 요청·스팸을 일반 제안보다 우선 처리한다.
- 리뷰에는 금지 내용, 광고/이해관계, 신고, 숨김·복원, 악의적 반복 신고, 이의제기를 포함한 운영 기준을 둔다.
- 익명 피드백은 회신 불가능할 수 있음을 명시한다. 현재 오프라인 피드백은 다음 제출 때 재전송되므로 즉시 접수와 혼동시키지 않는다.
- 긴급 보안·개인정보 의심 제보는 일반 문의와 다른 알림 경로로 담당자에게 전달한다.

### 4.4 인프라·백업·장애 복구

- 기존 기록에는 Supabase Free 프로젝트가 9/18 자동 일시정지되어 인증 문제가 장시간 지속된 이력이 있다. 현재 health는 정상이다. 추가된 ping만으로 가용성이 보장된다고 보지 않는다.
- Supabase 공식 안내상 Free는 비활성 프로젝트가 일시정지될 수 있고 Pro는 비활성 일시정지를 피할 수 있다. 회원 서비스를 정식 운영한다면 요금제·백업·복구 조건을 확정해야 한다. [Supabase 운영 체크리스트](https://supabase.com/docs/guides/deployment/going-into-prod)
- 보관 대상은 DB뿐 아니라 Auth 데이터 복구 범위, 저장 파일/사진 원본, 마이그레이션, 환경변수 목록, 도메인/DNS 설정과 계정 접근 복구 수단이다. 비밀값은 문서나 Git에 넣지 않는다.
- 백업 ‘존재’와 복원 ‘가능’을 구별한다. 별도 검증 환경에서 복원하고 로그인·저장·공유 동작까지 확인한다. 복원 뒤 삭제 요청한 데이터가 되살아나는 상황의 처리도 정한다.
- 초기 제안 목표: 최대 24시간 데이터 손실 허용(RPO), 4시간 내 복구(RTO). 운영 시간·예산·요금제로 달성 가능한지 확인하고, 달성 못하면 약속을 조정한다. 현재 달성했다는 판정이 아니다.
- 장애 절차: 탐지 → 담당자 확인 → 쓰기 제한/문제 기능 비노출 판단 → 상태 안내 → 롤백/복구 → 데이터 무결성 검증 → 사후 기록. 위험한 DB 변경은 코드 롤백만으로 되돌릴 수 없으므로 따로 계획한다.
- 도메인 갱신, 결제수단 만료, 계정 MFA·복구 코드, 주요 서비스 상태 알림, 비용 상한/경보를 관리한다.

### 4.5 보안·개인정보 일상 운영

- 서비스 역할 키는 서버와 제한된 운영 도구에서만 사용. 프런트엔드 공개 키와 구분하고, 로그·문서·지원 메시지로 비밀값을 전달하지 않는다.
- 관리자 권한은 개인별 계정과 최소 권한으로 관리하고 퇴사/협업 종료 시 회수한다. preview 환경이 운영 개인정보를 임의로 쓰거나 수정하지 않게 한다.
- 데이터 목록표에 필드별 목적·저장 위치·접근자·보존 기간·파기 방법을 기록한다. 피부·모발 프로필도 자유서술에서 의료 정보가 들어올 가능성을 검토하고 불필요한 수집을 줄인다.
- 계정 삭제, 마케팅 철회, 데이터 열람 요청은 본인 확인과 처리 기록을 포함한다. 정책의 ‘즉시 삭제’와 백업·법적 보존 예외가 충돌하지 않게 설명한다.
- 정기 보존기간 정리 작업은 실행 성공뿐 아니라 지워진 건수·실패 경보를 확인한다.
- 취약점 패치 일정과 보안 사고 대응 연락망을 지정한다. 모든 보안 경고를 방치하거나 모든 경고를 실제 침해로 오인하지 않는다.

### 4.6 모바일 품질·접근성·성능·SEO

- 실제 iPhone Safari와 Android Chrome에서 지도 드래그/확대, 시트 높이, 뒤로가기, 키보드, 긴 지점명, 위치 허용·거부, 외부 지도 앱 전환을 검증한다.
- 여행 환경을 반영해 느린 통신, 재연결, 데이터 절약 모드, 로그인 만료, 저장 동기화 충돌, 앱 복귀를 확인한다. 해외 사용자의 시간대는 OPS-05로 별도 해결한다.
- 키보드만으로 탐색, 보이는 포커스, 스크린리더 레이블, 색상 외 구분, 글자 확대, 시트 포커스 복귀를 검증한다. 지도 대안인 목록에서도 주요 작업을 수행할 수 있어야 한다.
- 현재 PWA는 오프라인 안내·일부 정적 리소스 수준이다. 장소·지도 전체가 오프라인 작동한다고 홍보하지 않는다. 서비스워커 갱신과 오래된 캐시도 테스트한다.
- 빌드 출력의 최초 로드 JS는 지도 약 374kB, 상세 약 333kB였다. 이 수치만으로 느리다고 확정하지 않는다. 실기기·네트워크별 체감과 지도 조작 가능 시각을 측정한다.
- 성능 이벤트 수집은 확인했다. 다만 QA 트래픽 포함 가능성·표본 편향·기기 구분 부족 때문에 수집치만으로 실제 관광객 성능 합격을 판정하지 않았다. 모바일/데스크톱별 75백분위 LCP·INP·CLS를 보는 것이 적절하다. [Web Vitals 공식 기준](https://web.dev/articles/vitals)
- 정식 도메인과 기본 sitemap/canonical은 이미 반영되어 있다. 도메인을 다시 구매해야 하는 상태가 아니다. 이후 기사·상품별 메타데이터, 대표 이미지, 검색 수집 상태, 비공개/검수 경로 noindex, 중복 도메인 처리, 깨진 외부 링크를 점검한다.

### 4.7 성과 지표와 운영 대시보드

처음에는 가입자 수보다 ‘여행 결정을 실제로 도왔는가’를 측정하는 것이 좋다. 아래는 제안 지표이며 현재 측정 완료값이 아니다.

| 종류 | 최소 지표 |
|---|---|
| 사용자 가치 | 검색 → 상세 열람 → 저장 → 길찾기 전환, 재방문, 결과 없는 검색 |
| 데이터 신뢰 | 검증된 장소 비율, 임시 위치 수, 오래된 영업시간 비율, 오류 제보 해결 시간 |
| 계정 품질 | 로그인/복구 성공률, 저장 실패율, 동기화 오류, 탈퇴 실패 |
| 운영 품질 | 문의 미처리 수·처리 시간, 신고 미처리 수, 백업/정리 작업 성공 |
| 기술·비용 | 정식 도메인 가용성, 기능별 오류, 모바일 성능, DB/지도/메일 사용량·청구 예상 |

관광객의 정확한 위치·검색어 원문·개인 식별자를 무조건 수집할 필요는 없다. 지표별 필요한 최소 정보와 보존 기간을 먼저 정하고, 분석 도입에 맞춰 개인정보 안내를 갱신한다.

## 7. 추가 확인이 필요한 사실과 질문

### 운영자가 알려줄 사항

1. 첫 출시는 **무료 탐색·저장 중심**, **광고·제휴 포함**, **예약·결제·판매 포함** 중 어디까지인가?
2. 핵심 이용자와 우선 국가/언어, 목표 출시일, 운영 인원, 월 운영 예산은 무엇인가?
3. 법적 운영 주체와 실제 지원 메일은 무엇이며, 현재 실사용자가 있는가?

### 관리자 화면에서 확인할 사항

- Vercel/Supabase 실제 요금제·청구·사용량, 프로덕션 배포 SHA와 Node 버전.
- 도메인/DNS 갱신과 소유 계정, WAF/봇 차단, 프로덕션·프리뷰 환경변수 존재 여부.
- Supabase 마이그레이션 이력, RLS/컬럼 권한과 Security Advisor, 사용하지 않는 인증 제공자의 활성화 의도.
- SMTP, 발신 도메인 DNS, Auth Site URL/Redirect allowlist, CAPTCHA·발송/가입 제한.
- 백업과 복원 기록, 예약 삭제 작업, 경보 수신자, 운영 계정 MFA/복구 접근.

이번에 Vercel CLI는 로그인되어 있지 않아 콘솔 정보를 읽지 못했다. 직접 DB 연결도 인증서 검증 오류로 중단했다. 보안 검증을 끄고 우회하지 않았으며, 이 영역은 미확인으로 남겼다. API 최소 읽기 결과와 저장소 SQL만으로 모든 관리자 설정을 확정하지 않는다.

운영 도구도 정리할 필요가 있다. CI는 Node 20, 운영 smoke는 Node 24로 달라 지원되는 LTS 버전으로 일치시키는 것을 권장한다. 현재 Vercel 기본 제공 버전은 24.x다. [지원 Node.js 버전](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions)

**Vercel CLI 59.10.0은 오래된 버전이므로 최신 버전으로 업데이트를 강력히 권장한다.** 세션에서 59.25.4 업데이트가 안내됐으며 최신 호환성과 에이전트 기능 개선을 위해 `npm i -g vercel@latest` 또는 `pnpm add -g vercel@latest`를 사용할 수 있다. 이 검토에서는 설치·업데이트하지 않았다.

## 8. 검토 산출물과 변경 범위

- 이 보고서와 읽기 전용 집계/시간대 재현 스크립트만 추가했다.
- 앱 코드, 계정, 공유 데이터, RLS, 배포, DNS, 요금제, 비밀키는 변경하지 않았다.
