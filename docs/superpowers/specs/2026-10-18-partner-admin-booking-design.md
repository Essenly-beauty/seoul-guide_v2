# 업체 관리자·예약 대시보드 설계

작성일: 2026-10-18 · 상태: 대화에서 승인한 범위의 문서 검토본

> 최신 범위 변경: 사용자는 일반 앱 정보·사진은 운영팀이 관리하고, 업체는 예약용 메뉴·패키지·날짜·시간과 선택형 담당자를 관리하도록 요청했다. 기존의 자유 추가 컬럼 논의는 철회됐다. 아래의 직원별 일정 제외·매장당 동시 수용 1건·업체 일반 정보 편집 범위는 [예약 운영 개정안](2026-10-18-partner-reservation-operations-design.md)의 검토 대상이다. 이전 구현 이력과 보안·결제·배포 조건은 보존하며, 개정안은 구현 완료를 뜻하지 않는다.

## 1. 목표와 범위

미용실·네일샵·헤드스파가 직접 카테고리와 메뉴를 관리하고, 예약 현황을 확인하는 공통 업체 관리자 기능을 기존 웹앱에 추가한다. 첫 제휴 업체 한 곳으로 검증한 뒤 같은 구조로 확대한다. 현재 확정된 제휴 업체는 없다.

빠른 출시를 위해 **설정 가능한 공통 관리자**를 선택한다. 업체마다 별도 페이지를 개발하거나 자유로운 화면 제작 도구를 제공하지 않는다. 카테고리·메뉴·노출 순서·영업시간은 업체가 바꾸고, 화면 구조와 필수 데이터 형식은 플랫폼이 관리한다.

이 문서는 두 작업의 경계를 정의한다. **다음 구현 계획의 대상은 A단계만**이며, B단계는 별도 상세 설계와 승인을 거친다.

단계 구분은 개발 순서이지 서로 독립된 서비스라는 뜻이 아니다. **고객 앱에서 예약하고 업체가 같은 예약을 관리하는 하나의 흐름**이 최종 결과다. A단계부터 고객 앱이 사용할 메뉴·시간·권한의 공통 기준을 설계하며, 관리자 화면만 동작하는 상태를 예약 기능 완료로 보지 않는다.

| 단계 | 제공 범위 | 완료의 의미 |
| --- | --- | --- |
| A. 업체 운영 기반 | 업체 권한, 카테고리·메뉴 관리, 영업시간·차단 시간, 대시보드 진입점 | 승인된 업체가 실제 저장된 설정을 관리할 수 있음. 고객 예약·결제는 열리지 않음 |
| B. 실제 예약 연결 | 고객 예약, 중복 예약 방지, 결제·취소·환불, 예약 목록·대시보드 집계 | 제휴·결제·정책 조건과 검증을 충족한 업체만 고객에게 예약을 제공함 |

대화에서 선택한 방향은 즉시 확정, 업체별 메뉴 관리, 예약 대시보드, 빠른 초기 출시다. 아래의 1인 예약·동시 수용 1건·언어 구성은 이를 위한 초기 설계안이며 이 문서 검토에 포함한다. 예약금의 총금액 차감 방식은 기본 제안으로 두되, 금액과 취소 정책은 사업자 승인 전 확정하지 않는다.

## 2. 기존 서비스와 연결

- 현재 Next.js 앱과 Supabase 로그인·데이터베이스를 재사용한다. 새 인증 서비스나 별도 관리자 앱을 도입하지 않는다.
- 관리자 경로는 `/partner` 아래에 둔다. 고객 화면의 기존 메뉴 구조를 이번 단계에서 바꾸지 않는다.
- 기존 `components/booking/booking-sheet.tsx`는 고정 서비스·시간·가격을 사용하는 시연용이다. 실제 예약 성공 처리로 재사용하지 않는다.
- 현재 `/bookings` 및 `/bookings/:id`는 `/menu`로 이동한다. B단계 검증 전 이 리다이렉트를 제거하거나 예약 가능 버튼을 공개하지 않는다.
- 공개 장소 카탈로그의 장소 정보는 업체 소유권 증명이 아니다. 기존 장소를 일괄 예약 가능 업체로 전환하지 않는다.
- 앞서 진행한 서비스 신뢰도·지하철 UX 수정은 보존한다. 예약 설계 완료가 기존 품질 개선이나 배포 전 검증의 완료를 뜻하지 않는다.

### 고객 앱 ↔ 업체 관리자 연동 계약

고객용과 업체용 화면은 서로 다른 표현과 권한을 갖지만, 업체·메뉴·예약 자원·예약의 식별자와 서버의 저장 기록을 공유한다. 앱에 별도 고정 메뉴나 시간표를 복사해 관리하지 않는다. 고객에게 공개할 정보와 업체 전용 정보는 각각 권한에 맞게 조회한다. 다음 표의 고객 예약 동작은 B단계 공개 조건 충족 후 제공하며 A단계에서 조기 공개하지 않는다.

| 업체 관리 또는 예약 이벤트 | 고객 앱에서의 결과 | 업체 관리자에서의 결과 |
| --- | --- | --- |
| 공개 조건을 충족한 메뉴 등록·수정 | 같은 메뉴의 이름·가격·소요시간·예약금 안내를 조회 | 저장한 값과 공개 여부 확인 |
| 메뉴·카테고리 숨김 또는 보관 | 신규 예약 선택에서 제외. 유효한 점유·기존 예약은 당시 조건 유지 | 기존 예약은 계속 조회·처리 가능 |
| 영업시간·휴무·차단 시간 변경 | 같은 예약 자원 기준으로 가능한 날짜·시간 재계산 | 기존 점유·예약을 침해하는 변경은 거절 |
| 고객이 결제 진행 | 결제 대기로 표시하며 아직 확정이라고 안내하지 않음 | 같은 자원은 임시 점유되지만 확정 예약 집계에는 포함하지 않음 |
| 결제 검증 및 예약 확정 | 예약번호·메뉴·시간·금액이 담긴 예약 상세 제공 | 같은 예약번호의 건이 목록·해당 날짜 집계에 반영 |
| 고객 또는 업체의 승인된 취소 | 같은 예약의 취소 상태와 별도 환불 진행 상태 확인 | 목록·집계·환불 처리 항목이 함께 갱신됨 |
| 방문 완료·노쇼 처리 | 내 예약에서도 같은 처리 상태 확인 | 같은 예약의 상태 및 변경 이력 반영 |

고객 앱의 기본 여정은 **업체 상세 → 메뉴 선택 → 날짜·시간 선택 → 예약자 정보·총금액·예약금·취소 조건 확인 → 결제 → 확정 상세 → 내 예약 조회·취소**다. 로그인이 필요해지면 선택을 보존하되 로그인 후 가격과 시간의 유효성을 다시 확인한다. 유효한 점유가 없는 판매 중단 메뉴나 만료된 점유로 새 결제를 시작하지 않는다.

- 예약 생성·취소·방문 처리는 공통 서버 규칙을 거친다. 각 화면이 별도로 성공 상태를 만들거나 대시보드 숫자만 수정하지 않는다.
- 메뉴·시간 선택 시 최신 정보를 조회하고, 결제 직전에 다시 검증한다. 유효한 기존 점유는 고정된 가격·조건을 사용한다. 다른 고객이 먼저 점유한 경우 결제 대신 시간 재선택을 안내한다.
- 양쪽 화면은 동작 성공 후 및 화면 진입·복귀 시 재조회한다. B단계에서 열린 예약 목록·상세·대시보드는 활성 화면에서 30초 간격으로 재조회하고 마지막 조회 시각을 표시한다. 결제·취소의 서버 검증은 이 주기를 기다리지 않는다.
- 통신 실패 시 이전 내용을 최신 상태로 표시하지 않는다. 갱신 실패를 알리고 재시도할 수 있게 한다. 알림 수신 여부는 예약 상태의 근거가 아니다.
- 취소로 점유가 해제되더라도 해당 시간이 영업시간·차단 조건을 만족할 때만 신규 예약에 다시 제공한다. 환불 진행과 예약 자원 해제를 혼동하지 않는다.
- A단계 구현 계획에는 공유 식별자, 공개 가능 조건, 금액·시간 단위, 공개용 정보 범위를 포함한다. B단계에서 고객 흐름을 연결하기 위해 별도의 메뉴·시간 데이터 체계를 다시 만들지 않는다.

## 3. 업체가 설정하는 항목

### 업종과 카테고리

- 플랫폼 업종은 미용실·네일샵·헤드스파로 시작하며, 업체가 해당 업종을 복수 선택할 수 있다. 검색용 업종과 업체 내부 카테고리를 구분한다.
- 업체 내부 카테고리는 직접 추가·수정·순서 변경·숨김·보관할 수 있다. 예: 커트, 컬러, 네일 케어, 스파 코스. 예시는 실제 메뉴로 자동 등록하지 않는다.
- 카테고리를 숨기거나 보관하면 해당 메뉴의 신규 노출도 중단한다. 기존 예약은 유지한다. 다시 공개할 때 개별 메뉴의 숨김 상태는 유지한다.
- 메뉴가 있거나 예약 이력이 있는 카테고리는 영구 삭제 대신 보관한다.

### 메뉴

공통 필드는 이름, 설명, 카테고리, 총 서비스 가격(KRW 양의 정수), 소요시간(양의 정수 분), 정리시간(0 이상 정수 분), 노출 여부, 표시 순서다. 이름·설명은 한국어와 영어를 따로 입력한다. 관리자 UI는 한국어, 초기 고객 예약 UI는 영어를 기준으로 한다.

- 초안은 일부 정보가 없어도 저장할 수 있지만, 예약 공개에는 이름·설명·가격·소요시간·영문 안내의 업체 확인이 필요하다.
- 첫 버전은 정액·정시 서비스만 판매한다. 변동 가격, 직원별 가격, 복잡한 추가 옵션은 제외한다. 필요한 경우 별도의 고정 패키지 메뉴로 등록한다.
- 예약금은 승인된 정책에 따라 KRW 양의 정수로 별도 저장하며 총금액을 초과할 수 없다. 초안에서는 미설정 상태를 허용하되, 임의 기본값으로 실제 예약을 열지 않는다. 예약금 없는 무료 예약은 첫 버전의 판매 방식에 포함하지 않는다.
- 가짜 후기·예시 가격·미확인 이미지를 생성하지 않는다. 첫 버전에 이미지 업로드를 추가하지 않고, 승인된 실제 사진이 없으면 이미지 없이 표시한다.
- 메뉴 수정·숨김·보관은 신규 예약에만 적용한다. 기존 예약은 예약 당시 메뉴명·가격·시간·예약금·취소 정책의 사본을 보존한다.

### 영업시간과 예약 가능 시간

- 주간 영업시간, 휴게시간, 날짜별 휴무·차단 구간을 설정한다. 첫 화면은 날짜와 시간 목록 방식으로 구성하며 드래그 캘린더는 제외한다.
- 첫 버전의 시간 구간은 같은 한국시간 날짜 안에서 시작하고 종료한다. 자정을 넘는 영업·예약은 제외하며, 시작이 종료보다 늦거나 같은 구간과 중복 영업 구간은 저장하지 않는다.
- 초기에는 업체당 공유 예약 자원 하나, 동시 수용 한 건, 예약당 고객 한 명을 기준으로 한다. 메뉴별로 별도의 동시 수용량을 만들지 않는다.
- 예약 가능한 연속 구간은 서비스 소요시간과 정리시간을 모두 수용해야 한다. 영업시간 밖·휴게시간·차단 구간은 예약할 수 없다.
- 시간 계산은 `Asia/Seoul` 기준으로 표시하고, 실제 시각은 UTC로 저장한다. 종료 시각과 다음 시작 시각이 같은 예약은 겹치지 않는 것으로 본다.
- B단계에서는 이미 확정된 예약이나 유효한 결제 대기 점유를 수용할 수 없게 만드는 영업시간 변경·차단을 거절하고 충돌 내역을 보여준다. 설정 변경으로 예약을 취소하지 않는다.
- 다른 채널에서도 같은 자리를 판매하면 즉시 확정이 불가능하므로, 초기 파트너는 제공한 예약 구간을 이 서비스용으로 확보해야 한다. 실제 합의는 예약 공개 조건이다.

## 4. 관리자 화면과 역할

| 경로 | 책임 | A단계 제공 상태 |
| --- | --- | --- |
| `/partner` | 준비 상태, 다음 예약, 처리할 업무, 집계 확인 | 메뉴·시간 설정 상태는 실제 데이터로 표시. 예약 영역은 ‘예약 기능 연결 전’으로 명시 |
| `/partner/services` | 카테고리와 메뉴 관리 | 실제 저장·수정·숨김·보관·순서 변경 |
| `/partner/availability` | 영업시간, 휴무·차단 시간 관리 | 실제 설정 저장 및 시간 유효성 검사 |
| `/partner/settings` | 업체명·연락처·주소·업종 관리 | 일반 정보 수정. 계약·예약금·취소 정책은 운영자 승인 항목으로 분리 |
| `/partner/reservations` | 예약 검색·상세·상태 변경 | B단계에서 제공. A단계에서는 조작 가능한 시연 목록을 만들지 않음 |

운영자가 소유권을 확인한 계정에만 업체 접근 권한을 부여한다. 초기에는 업체 소유자 한 명을 허용하고, 직원 초대·역할 편집·여러 지점 관리 UI는 제외한다. 데이터 구조는 업체와 사용자의 연결을 별도로 관리해 이후 확장이 가능하게 한다.

고객은 자신의 예약만, 업체는 자신의 업체에 속한 예약과 운영에 필요한 연락 정보만 본다. 업체 소유자는 직접 플랫폼 운영자 권한을 얻거나 다른 업체의 소유자로 자신을 등록할 수 없다.

## 5. 예약 대시보드 정의 — B단계

첫 버전은 복잡한 그래프보다 당일 운영과 예외 처리에 집중한다. 모든 지표에 집계 기준을 표시하고, 기간을 섞어 하나의 매출 수치로 합치지 않는다.

| 항목 | 집계 기준 |
| --- | --- |
| 오늘 예약 | 서비스 시작일이 오늘인 확정·방문 완료·노쇼 건수. 취소·결제 대기는 제외 |
| 오늘 방문 예정 | 오늘 시작하며 아직 시작 시각이 지나지 않은 확정 예약 |
| 오늘 취소 | 서비스 날짜와 무관하게 취소 확정 시각이 오늘인 예약 |
| 환불 처리 필요 | 전체 기간 중 환불 요청이 있으나 완료되지 않은 건. 요청·처리 중·실패를 구분 |
| 다음 예약 | 현재 이후 시작하는 확정 예약을 시간순으로 표시 |
| 확인 필요 | 시작 시각이 지났으나 방문 완료·노쇼 등 처리가 되지 않은 확정 예약 |

- 오늘의 경계는 한국시간 00:00부터 다음 날 00:00 직전이다. 예약 생성일과 방문일을 혼동하지 않는다.
- 예약금 수납액은 결제 성공 시각, 환불액은 환불 성공 시각 기준으로 별도 표시한다. 예약금과 현장 잔액을 합산한 ‘실제 매출’은 현장 결제가 확인되지 않으므로 제공하지 않는다.
- 상태 변경 후 재조회, 화면 진입·복귀 및 활성 화면의 30초 간격 재조회, 수동 새로고침, 마지막 조회 시각을 제공한다. 첫 버전에서 실시간 스트리밍 연동을 약속하지 않는다.
- 조회 중·실제 0건·연결 전·권한 없음·조회 실패를 각각 구분한다. 오류를 0건으로 표시하거나 예시 예약·매출 그래프를 삽입하지 않는다.
- 예약 상세에는 메뉴·방문 시간·금액·고객 연락처·상태 변경 이력을 제공한다. 여권이나 의료 정보 등 예약에 불필요한 민감정보는 수집하지 않는다.

## 6. 예약금과 즉시 확정의 경계 — B단계

기본 제안은 **예약금을 총 서비스 금액에서 차감**하는 방식이다. 고객에게 총금액, 지금 결제하는 예약금, 현장 결제 예정 잔액, 취소·환불 조건을 결제 전에 함께 보여준다. 예약금이 있는데 ‘무료 예약’으로 표현하지 않는다. 방문 후 예약금을 일괄 돌려주는 보증금 방식은 첫 버전에서 제외한다.

정상 흐름은 다음과 같다.

1. 고객이 업체·메뉴·시간을 선택하면 서버가 최신 가격과 예약 가능 여부를 검증한다.
2. DB에서 예약 자원을 원자적으로 임시 점유하고, 가격·서비스·정책 사본을 고정한다.
3. 고객이 예약금을 결제한다. 결제 화면으로 돌아왔다는 사실만으로 성공 처리하지 않는다.
4. 서버가 결제사의 신뢰할 수 있는 결과와 주문·금액·통화·자원 점유를 확인한 후 예약을 확정한다. 업체 승인 대기는 없다.
5. 고객과 업체가 저장된 확정 내역을 확인한다. 외부 알림이 실패해도 확정 예약을 취소하지 않으며, 알림 실패는 별도로 추적한다.

예외 처리의 필수 계약:

- 결제 대기 점유는 유한한 만료 시간을 갖는다. 정확한 유효시간과 결제 취소 방식은 선정한 결제사의 동작에 맞춰 B단계에서 설계한다.
- 같은 시간에 여러 요청이 와도 DB 수준에서 하나만 배정한다. 앱에서 먼저 조회하는 검사만으로 중복을 막지 않는다.
- 중복 클릭·재시도·중복 결제 알림은 같은 주문을 중복 확정하거나 중복 환불하지 않는다.
- 점유 만료 후 늦게 결제가 성공하면 자동으로 예약을 되살리지 않는다. 충돌을 확인하고 환불 또는 운영자 확인 대상으로 기록한다.
- 결제 중 메뉴가 변경되어도 이미 고정된 결제 건의 금액을 몰래 바꾸지 않는다. 새 가격으로 진행하려면 고객에게 다시 안내한다.
- 예약 상태와 결제·환불 상태를 분리한다. 취소된 예약에도 환불 처리 중·실패 상태가 남을 수 있고, 실패는 재처리 가능해야 한다.
- 방문 완료·노쇼는 권한 있는 업체의 명시적인 처리로 기록한다. 시간이 지났다는 이유로 노쇼나 예약금 몰수를 자동 처리하지 않는다.
- 업체 취소 시 예약금 전액 환불을 기본 제안으로 둔다. 고객 취소 시점별 환불액, 추가 보상, 노쇼 처리는 법적 검토와 승인된 정책 없이 자동화하지 않는다.

## 7. 데이터와 접근 제어

### A단계의 책임

- `merchants`: 공개 업체 정보와 운영 상태. 기존 공개 장소와 연결하더라도 별도 소유권 검증을 요구한다.
- `merchant_memberships`: 업체와 인증 사용자 연결. 쓰기 권한은 신뢰된 운영 절차에만 부여한다.
- `merchant_categories`, `merchant_services`: 업체별 카테고리·정액 메뉴·노출 순서. 교차 업체 참조를 허용하지 않는다.
- 영업시간·휴게시간·날짜별 차단 데이터: 업체별 예약 자원의 제공 범위. 실제 예약 점유와는 구분한다.
- 변경 이력: 접근 권한, 메뉴·가격, 운영시간 변경의 담당자와 시각을 기록한다. 고객 개인정보와 비밀키를 로그에 남기지 않는다.

### B단계에서 추가하는 책임

예약 및 임시 점유, 예약 당시 메뉴·정책 사본, 결제·환불 원장, 외부 이벤트 중복 방지, 예약 상태 변경 이력을 추가한다. A단계에서 가상 결제나 확정 예약 데이터를 채워 인터페이스를 흉내 내지 않는다. B단계의 구체적인 테이블·결제사 SDK·배치 복구 방식은 해당 상세 설계에서 확정한다.

### 공통 보안 요건

- 외부에 노출되는 테이블에는 RLS와 최소 권한을 함께 적용한다. 서버 요청에서도 인증된 사용자와 업체 연결을 확인한다. [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)
- 클라이언트가 보낸 `merchant_id`나 사용자가 수정 가능한 프로필 메타데이터를 권한의 근거로 삼지 않는다. 변경 전후 행 모두 같은 업체 권한 범위에 있어야 한다.
- 카테고리·메뉴 등 관계 키가 같은 업체에 속하는지 DB와 서버에서 보장한다. 다른 업체 ID를 직접 API로 전달하는 우회를 검증한다.
- 기존 Supabase 서버 인증을 활용하고, 브라우저가 전달한 사용자 객체만으로 인증 완료를 판단하지 않는다. [서버 클라이언트 공식 문서](https://supabase.com/docs/guides/auth/server-side/creating-a-client)
- 공개 업체 조회는 공개용 필드로 제한한다. 회원 연결·고객 연락처·결제 원장은 공개 조회나 공유 캐시에 포함하지 않는다.
- 서비스 역할 비밀키는 제한된 서버 코드에서만 사용하며, 관리자 편의를 위해 일반 업체 요청의 RLS를 우회하지 않는다.
- 기존 계정 삭제는 인증 사용자를 삭제하는 경로다. A단계에서 업체 소유자 계정은 업체 정리 절차 없이 삭제할 수 없도록 연결 검사를 추가하고 지원 경로를 안내한다. B단계에서는 예약·금융 이력이 연쇄 삭제되지 않게 하고 승인된 보관·비식별화 정책을 적용한다.
- 기능 비활성화 시 신규 예약을 차단하되, 이미 존재하는 예약 조회·취소·환불 처리 통로는 유지한다.

## 8. 첫 구현 계획의 완료 조건 — A단계

1. 승인된 계정만 관리자에 접근하며, 업체 A 사용자는 직접 API 요청을 해도 업체 B 정보를 읽거나 수정할 수 없다. 자신의 업체 연결도 임의 변경할 수 없다.
2. 카테고리·메뉴 추가, 수정, 순서 변경, 숨김, 보관이 실제 DB에 저장되고 재접속 후 유지된다.
3. 금액·시간·업체 소속·필수 항목을 검증한다. 예약금 미설정을 0원으로 간주하지 않는다. 초안 저장과 예약 공개 조건을 구분한다.
4. 잘못된 영업시간·휴게시간·차단 범위를 거절한다. 메뉴마다 독립적인 예약 수용량이 생기지 않는다.
5. 업체가 없는 계정, 초안 업체, 조회 실패, 저장 실패에 대해 상태를 명확히 표시한다. 저장 실패 후 성공 안내를 보여주지 않는다.
6. 대시보드는 실제 설정 상태와 예약 연결 전 상태를 보여준다. 예약·매출·고객 샘플 데이터를 실제 실적으로 표시하지 않는다.
7. 업체 소유자 계정 삭제 경로가 업체 데이터를 고아 상태로 남기지 않도록 보호하고, 업체 종료·계정 정리를 요청할 지원 경로를 안내한다.
8. 접근 제어·입력 검증·숨김/보관·조회 실패 테스트와 모바일/데스크톱 화면 점검을 수행한다. 타입 검사·린트·관련 테스트·전체 테스트·빌드를 통과한다.
9. 실제 운영 DB 변경, 업체 접근 권한 부여, 외부 서비스 설치, 공개 배포는 별도 확인 후 진행한다. 이 기획서 작성은 그러한 작업을 수행하지 않는다.
10. 고객 앱 연결에 필요한 공유 식별자·공개 조건·금액·시간 단위가 구현 계획과 데이터 모델에 명시되어 있다. 관리자와 고객 앱에 서로 다른 메뉴·시간표를 만드는 구조는 허용하지 않는다.

## 9. 실제 예약 공개 전 충족할 조건 — B단계

- 제휴 업체 한 곳이 메뉴·가격·소요시간·사진 사용 권한·고객 응대 방법을 확인하고, 다른 채널과 겹치지 않는 예약 구간 제공에 합의한다.
- 결제 계약 주체, 지원 국가·통화, 예약금 수납·정산 주체, 수수료, 환불 부담 주체를 확정한다. 결제사를 임의 선택하거나 이미 연결된 것처럼 표시하지 않는다.
- 예약금 액수, 고객 취소 기준, 노쇼 처리, 업체 취소, 개인정보 보관·탈퇴 정책을 승인하고 버전으로 보존한다. 임의의 ‘24시간 전 환불’이나 ‘노쇼 100% 몰수’를 기본값으로 넣지 않는다.
- 실제 제공업체의 테스트 환경에서 결제 성공·실패·중복 알림·금액 불일치·점유 만료 뒤 성공·환불 실패/재처리를 검증한다. 결제 연동 발견 도구가 이전에 오류를 반환했으므로 연동 완료로 간주하지 않는다.
- 동시 예약 요청, 다른 메뉴 간 시간 겹침, 한국시간 날짜 경계, 예약 중 영업시간 변경, 메뉴 수정 후 기존 예약 보존을 검증한다.
- 고객 계정과 업체 계정을 분리한 종단간 테스트로 `업체 메뉴·시간 등록 → 고객 앱에서 선택 → 결제·확정 → 업체 목록·집계 확인 → 고객 취소 → 업체 취소·환불 상태 확인`을 검증한다. 별도 예약으로 방문 완료·노쇼 처리도 검증하고, 각 예약의 고객 상세에 같은 상태가 반영되는지 확인한다.
- 위 테스트에서 양쪽 예약번호·메뉴·방문 시각·총금액·예약금·상태를 대조한다. 메뉴 숨김, 시간 차단, 동시 예약, 조회 실패, 환불 실패 상황도 양쪽에 일관되게 나타나야 한다. 각 화면을 따로 테스트하는 것만으로 연동 완료를 선언하지 않는다.
- 고객에게 확정 사실과 취소 경로를 전달하는 알림 채널, 실패 확인·재처리 책임을 정한다. 화면에서의 예약 확인과 외부 알림 성공을 혼동하지 않는다.
- 미해결 결제·환불 예외를 확인할 운영 담당자가 있고, 신규 예약을 중단하는 수단과 기존 예약 지원 통로를 검증한다.
- 기존 품질 개선의 잔여 항목까지 포함한 배포 전 검사와 사용자의 최종 확인 후 배포한다. A단계 완료를 실제 예약 서비스 오픈으로 표현하지 않는다.

## 10. 이번 범위에서 제외

자유로운 페이지·폼 제작, 임의 필드·CSS·스크립트, 직원별 스케줄과 권한 UI, 다인·그룹 예약, 외부 캘린더 동기화, 다지점 운영 UI, 쿠폰·포인트, 현장 결제 정산, 자동 번역, 고급 매출 분석, 의료 서비스 예약은 제외한다. 예약 시간 변경은 첫 버전에서 직접 변경 기능을 제공하지 않고 승인된 취소·재예약 흐름으로 처리한다.

이 설계는 빠른 시작을 위해 기능을 줄이되, 실제 데이터 저장·업체별 권한·중복 예약 방지·정확한 결제 안내는 생략하지 않는 것을 기준으로 한다.
