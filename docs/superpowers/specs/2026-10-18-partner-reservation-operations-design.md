# 업체별 예약 운영 관리 — 범위 개정안

작성일: 2026-10-18 · 상태: 사용자 요구 범위 확인, 세부 설계 검토안

## 1. 이번에 확정한 방향

사용자의 최신 지시를 우선한다. 앱의 일반 소개·사진·콘텐츠는 플랫폼 운영팀이 관리하고, 업체 관리자는 **예약에 필요한 메뉴·패키지·담당자·예약 가능 일정과 실제 예약 처리**에 집중한다.

앞선 공통 컬럼 + 자유 추가 컬럼, 이미지 업로드, 콘텐츠 게시 도구 논의는 이번 구현 범위에서 제외한다. 업체별 차이는 임의의 컬럼이나 화면을 만드는 방식이 아니라 예약 운영에 의미가 정해진 항목과 선택 기능으로 지원한다.

이 문서는 기존 `2026-10-18-partner-admin-booking-design.md`의 업체 정보 편집 책임, 담당자 제외, 매장당 동시 수용 1건이라는 범위를 대체하는 개정안이다. 기존 인증·업체 격리·메뉴·일정 저장 구현은 재사용한다. 기존 A3 UI의 미완료 검토·검증은 완료된 것으로 처리하지 않는다.

**완료 기준은 고객 웹앱의 예약과 업체의 예약 관리가 같은 저장 기록으로 연결되는 것**이다. 관리자 입력 화면이나 달력 모양만 완성한 상태를 예약 서비스 완성으로 보지 않는다.

## 2. 구현 접근 비교

| 접근 | 장점 | 비용·제약 |
| --- | --- | --- |
| 공통 예약 관리자 + 업체별 기능 설정 — 권장 | 같은 예약 규칙과 앱 흐름을 유지하면서 카테고리·메뉴·담당자·일정을 업체가 관리 | 지원할 설정의 의미와 검증을 플랫폼이 명확하게 정해야 함 |
| 미용실·네일·헤드스파별 별도 관리자 | 업종별 표현을 세밀하게 최적화 가능 | 화면·예약 규칙·테스트가 중복되고 업종을 함께 운영하는 숍에 불리함 |

빠른 출시와 업체별 차이를 함께 지원하기 위해 첫 번째 방식을 제안한다. 업종만 보고 담당자 선택을 강제하지 않는다. 네일샵·헤드스파도 필요하면 담당자 선택을 사용할 수 있다.

## 3. 관리 책임

| 플랫폼 운영팀 | 업체 관리자 |
| --- | --- |
| 앱의 일반 업체 소개·사진·주소 등 공개 정보 관리 | 자기 숍의 예약용 카테고리·메뉴·패키지 추가·수정·판매 중지 |
| 업체 소유권 확인, 기존 앱 장소와 업체 연결 승인 | 담당자 추가·수정·신규 예약 노출 중지, 담당 메뉴 지정 |
| 계약·예약금·취소 정책 승인, 예약 공개 승인 | 영업일·근무일·휴무·차단 시간·예약 접수 범위 설정 |
| 결제·환불 예외 지원 및 운영 감사 | 자신의 예약 조회, 승인된 규칙에 따른 방문 완료·노쇼·취소 처리 |

일반 업체 소개와 예약 메뉴의 설명은 구분한다. 메뉴명·구성·가격·소요시간은 예약 상품의 일부이므로 업체가 관리한다. 기존 `/partner/settings`의 일반 업체 정보는 이 개정안을 적용할 때 읽기 전용 + 수정 요청 경로로 바꾼다. 버튼만 숨기지 않고 서버의 쓰기 허용 범위도 맞춘다.

담당자 등록은 **예약 대상인 직원 정보 등록**이다. 직원 로그인 계정 발급이나 관리자 권한 초대까지 포함하지 않는다. 첫 버전의 운영 계정은 기존 업체 소유자 구조를 유지한다.

## 4. 업체가 추가·수정하는 예약 항목

### 4.1 카테고리·메뉴·패키지

- 카테고리: 이름, 표시 순서, 사용 여부.
- 메뉴: 한국어·영어 이름과 설명, 카테고리, 총 가격, 시술 시간, 정리 시간, 판매 상태, 표시 순서.
- 패키지: 첫 버전에서는 **한 번 방문해서 받는 묶음 메뉴**로 취급한다. 구성 설명·총 가격·총 시술 시간·정리 시간을 하나의 예약 상품으로 저장한다. 여러 회차 이용권, 서로 다른 시간에 진행되는 시술, 여러 담당자의 연속 배정은 포함하지 않는다.
- 담당자 선택을 사용하는 숍은 메뉴마다 제공 가능한 담당자를 지정한다. 모든 담당자에게 모든 메뉴를 자동 배정하지 않는다.
- 담당자별 가격·시간 자동 가산은 첫 버전에서 제외한다. 차이가 있으면 명확한 별도 메뉴를 만들고 해당 담당자를 연결하는 방식을 제안한다.
- 예약금은 기존 승인 정책에 따른 별도 금액으로 유지한다. 미설정을 무료로 취급하지 않으며, 임의 추가 항목으로 금액·정책을 우회하지 못한다.
- 판매 중지·보관은 신규 예약에만 적용한다. 기존 예약의 메뉴명·가격·소요시간·담당자·정책 기록은 유지한다.

### 4.2 담당자

- 이름·직함·짧은 예약용 소개, 표시 순서, 신규 예약 노출 여부.
- 제공 가능한 메뉴·패키지, 주간 근무시간, 휴게시간, 날짜별 휴무·차단 시간.
- 일반 사진·이미지 관리는 운영팀 책임을 유지한다. 이번 단계에서 직원 이미지 업로드 기능을 별도로 추가하지 않는다.
- 담당자별 같은 시각의 활성 점유는 한 건으로 시작한다. 같은 담당자가 서로 다른 메뉴로 중복 예약되지 않도록 한다.
- 기존 예약이 남아 있는 담당자는 영구 삭제하지 않는다. 신규 예약 노출 중지는 가능하지만 기존 예약의 담당자와 이력을 지우지 않는다.

### 4.3 예약 가능 날짜·시간

- 매장의 주간 영업시간·휴게시간, 특정 날짜의 특별 영업시간·휴무·차단 시간.
- 예약을 받는 날짜 범위, 미리 예약해야 하는 시간, 시작 시간 간격. 값은 업체가 확인해 저장하며 임의의 영업 정책을 자동 공개하지 않는다.
- 담당자 선택형에서는 해당 담당자의 근무·휴게·휴무 일정도 함께 적용한다.
- 고객에게는 메뉴의 시술 시간 + 정리 시간을 모두 수용할 수 있는 시작 시간만 제공한다.
- 시각 기준은 `Asia/Seoul`, 실제 예약 시각은 UTC로 저장한다. 첫 버전에서 자정을 넘는 예약은 제외한다.
- 달력 화면은 이 설정과 기존 예약·결제 대기 점유로 계산한다. 업체가 날짜마다 별도 페이지를 만드는 방식은 제공하지 않는다.
- 이미 확정된 예약이나 유효한 결제 대기 점유를 침해하는 일정·수용량 변경은 거절하고 충돌을 안내한다. 설정 변경으로 예약을 몰래 취소하지 않는다.

## 5. 숍별 예약 방식과 수용량 — 제안

### 매장 예약형

담당자 선택을 사용하지 않는다. 고객은 메뉴 → 날짜·시간 순서로 선택한다. 모든 메뉴가 같은 매장 수용량을 공유한다. 메뉴를 하나 더 만든다고 예약 가능한 자리가 늘어나지 않는다.

### 담당자 선택형

고객은 메뉴 → 제공 가능한 담당자 → 날짜·시간 순서로 선택한다. 담당자가 근무하고 선택 메뉴를 제공할 수 있는 시간만 표시한다. 첫 버전에서는 담당자 직접 선택만 지원하며, ‘아무나 배정’과 자동 담당자 교체는 제외한다.

### 공통 제한

매장은 실제로 동시에 제공할 수 있는 예약 수를 설정한다. 담당자 선택형도 매장 전체 수용량을 초과할 수 없다. 예를 들어 담당자가 둘이어도 사용 가능한 시술 자리가 하나라면 같은 시간에 두 건을 확정하지 않는다. 숫자는 예시이며 실제 업체 설정으로 자동 등록하지 않는다.

초기에는 한 예약이 매장 수용량 한 단위와 선택한 담당자 한 명을 점유한다. 특정 룸·장비별 배정, 메뉴마다 다른 자리 사용량, 다인 예약은 제외한다. 이 단순 모델로 운영할 수 없는 숍은 검증 없이 예약을 공개하지 않는다.

예약 방식 변경과 수용량 감소는 기존 예약·유효 점유와의 충돌 검사를 거친다. 직원 수가 늘었다는 이유만으로 매장 수용량을 자동 증가시키지 않는다.

## 6. 고객 앱 ↔ 관리자 연결

| 업체 관리 또는 고객 행동 | 연결 결과 |
| --- | --- |
| 메뉴·패키지 저장 및 공개 조건 충족 | 연결된 업체의 고객 화면에서 같은 메뉴·금액·시간 조회 |
| 담당자·담당 메뉴·일정 설정 | 해당 숍에서만 담당자 선택 단계와 가능한 시간이 구성됨 |
| 휴무·차단·판매 중지 | 신규 예약 선택에 반영되며 기존 예약은 보존됨 |
| 고객 예약금 결제 검증 완료 | 같은 예약번호로 고객 상세·업체 예약 목록·일정에 반영 |
| 방문 완료·취소·노쇼 처리 | 양쪽 화면에서 같은 예약 상태를 조회하고 변경 이력을 남김 |

- 기존 공개 장소 ID와 업체 ID의 연결은 운영팀이 확인한다. 업체가 임의 장소 ID를 입력해 다른 숍을 편집할 수 없다.
- 고객 앱이 별도의 고정 메뉴·담당자·시간표를 사용하지 않도록 공통 서버 조회 경로를 사용한다. 관리자 전용 정보나 다른 고객의 개인정보는 공개 응답에 포함하지 않는다.
- 고객 선택 직후와 예약 확정 직전에 서버가 메뉴·담당자·일정·매장 수용량을 재검증한다. 경쟁 요청의 중복 점유 방지는 저장 계층에서 원자적으로 수행한다.
- 유효한 결제 대기 점유는 생성 당시의 메뉴·금액·소요시간·담당자·정책을 유지한다. 이후 메뉴 수정이나 신규 판매 중지가 진행 중인 결제의 조건을 바꾸지 않는다. 만료된 점유는 재사용하지 않고 현재 조건으로 다시 확인한다.
- 관리자에 저장한 정보가 고객에게 반영됐는지는 고객 권한의 실제 조회로 검증한다. 화면끼리만 값을 복사하거나 가짜 성공 응답으로 대체하지 않는다.
- 조회 실패는 0건이나 빈 시간표로 위장하지 않는다. 마지막 조회 정보와 갱신 실패를 구분하고 재시도를 제공한다.
- 예약·취소·방문 처리 성공 후 및 화면 복귀 시 재조회한다. 활성 예약 화면은 기존 설계의 30초 재조회와 수동 조회를 유지하며, 실시간 스트리밍 완료로 표현하지 않는다.

## 7. 관리자 화면 구성

- **예약 현황:** 오늘 예약, 시간순 일정, 처리 필요한 건. 확정 예약 연동 전에는 그 사실을 표시하고 샘플 예약·매출을 채우지 않는다.
- **예약 목록·상세:** 날짜·상태·담당자별 확인, 고객 연락 정보, 메뉴·담당자·시간·금액, 상태 변경 이력과 가능한 처리 버튼.
- **메뉴·패키지:** 카테고리와 상품 목록, 상세 편집, 담당자 연결, 판매 상태.
- **담당자:** 담당자 목록, 제공 메뉴, 근무·휴무 설정. 담당자 선택을 쓰지 않는 숍에는 불필요한 입력을 강제하지 않는다.
- **예약 일정·설정:** 매장 일정, 예약 가능 날짜 범위, 차단, 예약 방식, 동시 수용량.
- **업체 정보:** 운영팀이 관리하는 정보 확인과 수정 요청 경로.

사용자가 준 Naver Dashboard 참고 이미지는 상단 헤더·왼쪽 탐색·작업 목록과 상세 패널이라는 업무형 구성을 참고한다. 채팅·가상 통계·알림 뱃지를 기능 없이 추가하지 않는다. 데스크톱에서는 목록과 상세를 함께 보고, 모바일에서는 목록 → 상세로 전환하되 같은 작업을 제공한다.

## 8. 구현 단위와 연결 책임

1. **예약 운영 설정:** 기존 메뉴·일정 저장을 확장해 담당자·제공 메뉴·근무 일정·예약 방식·수용량을 관리한다. 업체 권한과 입력 검증, 충돌 버전을 유지한다.
2. **공통 예약 가능 시간과 고객 선택:** 같은 설정을 고객용 필드로 조회하고 메뉴·담당자·시간을 선택한다. 실제 점유와 기존 예약을 반영하며, 접수 비활성 상태에서는 확정 성공을 표시하지 않는다.
3. **예약·결제·관리자 처리 연결:** 임시 점유, 승인된 결제 연동, 즉시 확정, 예약 목록·일정·취소·환불·방문 처리를 같은 예약 기록으로 연결한다.

단위는 작업 순서일 뿐 별도 서비스가 아니다. 각 단위의 계획에 고객 앱과 업체 화면 사이의 계약·검증을 포함한다. 기존 A3 검토·SQL 테스트 격리 문제도 새 작업 전에 정리하거나 명시적으로 추적한다.

## 9. 완료 검증

1. 업체 A가 메뉴·담당자·일정을 추가·수정한 뒤 재접속해도 유지되며, 업체 B는 읽거나 수정할 수 없다.
2. 담당자 선택형과 매장 예약형의 고객 선택 단계가 각각 다르게 작동한다. 담당자를 지정하지 않는 숍에 빈 담당자 목록을 강요하지 않는다.
3. 담당자에게 연결되지 않은 메뉴, 휴무일, 매장 영업시간 밖, 시술+정리 시간이 부족한 구간은 예약할 수 없다.
4. 같은 담당자에 대한 동시 요청, 서로 다른 메뉴를 통한 동시 요청, 서로 다른 담당자라도 매장 수용량을 넘는 요청을 차단한다.
5. 기존 예약을 침해하는 일정 변경·담당자 제거·수용량 감소를 안전하게 처리한다. 신규 판매 중지 후에도 기존 예약의 조건과 처리 경로가 유지된다.
6. 고객 앱에서 실제 예약을 생성하고 업체 계정으로 같은 예약번호·메뉴·담당자·시간·금액을 대조한다. 취소·방문 처리 후 고객 상세도 확인한다.
7. 결제·환불의 성공·실패·중복 알림·점유 만료·재처리를 실제 제공업체의 테스트 환경에서 검증한다. 결제 화면 복귀만으로 확정하지 않는다.
8. 저장 실패, 동시 수정 충돌, 권한 회수, 모바일·데스크톱, 접근성·반응형과 기존 고객 화면 회귀를 검증한다.

## 10. 유지되는 공개·배포 조건

제휴 업체 확인, 실제 예약 구간 확보, 예약금·취소·환불 정책, 결제·수납·정산 책임, 실제 결제 제공업체 테스트 및 최종 배포 확인은 기존 설계의 조건을 유지한다. 담당자 기능 추가가 이 조건을 우회하지 않는다.

이 설계 문서는 기능 구현 완료, 결제 연동 완료, 운영 DB 변경, 실제 업체 계정 부여 또는 배포를 뜻하지 않는다. 운영 정보와 실제 예약 데이터는 사용자 승인 없이 변경하지 않는다.
