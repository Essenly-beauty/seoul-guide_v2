# 파트너 예약 관리자 UX 재설계안

2026-10-19 · 상태: 검토용 제안 / 앱 구현·배포 전

근거: [공식 자료 조사](../../../reports/design/2026-10-19-partner-admin-benchmark.md). 기존 승인된 [예약 운영 범위](2026-10-18-partner-reservation-operations-design.md)를 변경하지 않는다.

## 목적과 설계 맥락

미용실·네일샵·헤드스파의 사장님/예약 관리 담당자가 자기 숍의 메뉴·선생님·가능 일정을 관리한다. PC에서 초기 설정하고 모바일에서 당일 업무를 처리하는 사용을 우선 가정한다. 기기 선호 질문은 아직 미응답이므로 검증할 가정으로 남긴다. 한국어의 차분하고 명료한 운영 도구, 기존 민트 계열 브랜드와 연결하되 소비자 앱의 잡지형/세리프 표현은 업무 화면에 강제하지 않는다.

브레인스토밍 단계의 대안 비교 후 ‘운영 작업 공간’을 제안한다. 프런트엔드 디자인 스킬의 점진적 정보 노출·입력 레이블·키보드 포커스·반응형 지침을 검토용 시안에 적용한다. 실제 저장은 서버 응답과 재조회가 확인되기 전 성공으로 표시하지 않는다.

2026-10-19 오후 사용자 요청: 네이버 미용실 예약과 다른 예약 플랫폼, 국내의 깔끔한 관리자 대시보드를 참고해 개선·신규 기능. 근거는 [2차 조사](../../../reports/design/2026-10-19-partner-admin-benchmark.md) 6절. 홈·예약 목록·고객·통계·알림 설정을 추가했고, 예약 처리 규칙(완료·노쇼는 시작 후만, 취소 사유 필수, 철회 불가, 시간 변경 시 고객 알림)을 상세 패널에 넣었다.

2026-10-19 사용자 피드백으로 ‘예약 현황’과 ‘예약 가능 일정’을 **예약 캘린더** 한 화면으로 합쳤다. 요청: 구글 캘린더처럼 스케줄을 추가하면 시간·담당자·예약자 정보가 한눈에 보일 것, 빈 시간에서 예약 추가와 시간 막기·휴무를 둘 다 할 것, 헤어샵은 고객이 디자이너를 고를 수 있을 것.

운영 현황은 접수 비활성/연동 전이면 준비 상태와 다음 할 일을 보여준다. 예약 데이터가 없다고 가짜 0건·매출·알림을 만들지 않는다. 실제 조회 성공 후 빈 결과만 0건으로 표현한다. 검토용 시안에서만 명시적으로 ‘연동 후 예시’를 선택할 수 있다.

## 핵심 화면

### 예약 캘린더

- **일간(PC 기본):** 세로 열이 요일이 아니라 디자이너다. 미용실 관리 프로그램(네이버 예약·공비서 등)처럼 “누가 몇 시에 비는지”를 바로 본다. 열 머리에 근무시간과 예약 수. 근무 외는 빗금, 휴게는 옅은 띠, 막은 시간은 줄무늬+사유, 예약은 디자이너 색 블록(시간·고객·메뉴, 끝부분은 정리 시간). 현재 시각 선.
- **주간:** 구글 캘린더처럼 요일 열. 디자이너 칩으로 보고 싶은 사람만 고른다. 겹친 예약은 나란히 배치하고 좁으면 시작 시각·이름만. 날짜 머리를 누르면 그날 일간으로.
- **모바일:** 기본은 그날의 시간순 목록(예약·막은 시간·휴무 담당자). ‘타임라인’에서 디자이너 한 명씩. 추가는 하단 + 버튼, 상세·입력은 아래에서 올라오는 시트.
- **빈 칸 누르기:** 그 칸의 디자이너·시간이 채워진 선택지 [예약 추가] [시간 막기] [이 날 휴무]. 키보드 사용자는 ‘+ 추가’ 버튼으로 같은 선택지를 연다.
- **예약 추가(전화·방문):** 고객 이름·연락처·디자이너·메뉴(그 디자이너에게 연결된 판매 중 메뉴만)·날짜·시작·메모. 종료 시각은 메뉴 시간+정리 시간으로 자동 계산. 같은 디자이너 예약·막은 시간·휴무일·동시 예약 수 초과는 추가 불가, 근무시간 밖·휴게 겹침은 경고 후 허용(아래 질문 참조). 업체 입력 예약은 예약금 없이 현장 결제로 표시.
- **예약 상세:** 고객(가상)·연락처, 경로(앱 예약이면 “고객이 ○○ 디자이너를 직접 선택”, 전화·방문이면 “업체가 직접 입력”), 일시·정리 종료, 메뉴, 담당자, 요청 메모, 총액·예약금·현장 잔액, 방문 완료·노쇼·예약 취소. 상태 변경은 서버 반영 후 재조회가 원칙.
- **시간 막기·휴무:** 대상(매장 전체/디자이너)·날짜·시간·내부 사유. 기존 예약이 있으면 “막아도 기존 예약은 그대로” 경고. 휴무는 해당 날짜 예외로 저장되어 ‘기본 근무시간 › 특정 날짜’와 같은 데이터다.
- **예약 처리 규칙(네이버 예약·Fresha 참고):** 방문 완료·노쇼는 예약 시작 시간이 지난 뒤에만 활성화되고 처리 후 되돌릴 수 없다(확인 상자에 명시). 예약 취소는 사유 선택이 필수이며 고객에게 보인다. 앱 예약 취소의 환불은 승인된 정책에 따라 서버가 처리한다. ‘시간 변경’은 같은 입력 폼에서 날짜·시작·디자이너·메뉴를 바꾸고, 자기 자신과의 겹침은 제외하며, 저장 후 고객 변경 알림을 보낸다. **끌어서 옮기기(2026-10-19 사용자 요청으로 추가):** 확정 예약만 15분 단위로 다른 시간·디자이너(일간)·날짜(주간)로 끌 수 있고, 놓으면 점선 미리보기와 확인 상자(이전 → 새 시간, 겹침·근무시간·휴게 경고, 새 디자이너가 그 메뉴를 제공하지 않으면 차단)가 뜬 뒤 ‘변경 확정’으로만 반영된다(공비서·Fresha의 드래그 후 확인 방식). 되돌리기·Esc·패널 닫기는 원위치. 휴대폰은 길게 누른 뒤 끌고, 완료·노쇼·취소된 예약은 끌 수 없다. 키보드 사용자는 ‘시간 변경’ 폼을 쓴다. 길이 조절(끝 시간 드래그)은 메뉴 시간이 기준이므로 넣지 않는다.
- **시간 막기 반복:** ‘이 날만’ 또는 ‘매주 같은 요일’. 매주 반복은 서버의 근무시간 `blocks`(weekday) 규칙과 같은 데이터다. 막은 시간에 기존 예약이 있으면 경고만 하고 예약은 보존한다(공비서·Fresha와 동일).
- **검토 시나리오:** ‘현재 제공 범위’는 예약 블록 없이 근무·막은 시간만, ‘예약 추가’는 비활성. ‘예약 연동 후 예시’에서만 가상 예약을 보인다.
- 월간 보기 대신 작은 달력으로 날짜 이동. 끌어서 옮기기는 확인 상자를 거치므로 실수로 바뀌지 않는다.

터치 기기(v3.4): 예약 블록 위에서 바로 쓸면 화면이 스크롤되고, 350ms 길게 누른 뒤 끌면 옮긴다. 블록에는 `touch-action: pan-x pan-y`를 두고 길게 누른 뒤에만 `touchmove`를 막는다. 헤드리스 Chromium의 CDP 터치 이벤트로 두 경우를 검증했고, 실기기(iOS Safari) 확인은 남아 있다.

### 홈

- **오늘 KPI 띠(한 카드, 세로 hairline 분할):** 오늘 예약(지난주 같은 요일 대비 증감) · 방문 완료(남은 예약) · 노쇼(이번 주 누적) · 현장 결제 예정(예약금 제외). 숫자를 누르면 해당 필터가 걸린 예약 목록으로 간다(네이버 스마트플레이스 앱 홈 4카드 패턴). 예약 연동 전에는 ‘—’와 ‘예약 연동 후 집계’만 보이고 0건·매출을 지어내지 않는다.
- **할 일:** 설정·예약 상태에서 자동으로 찾은 항목만, 행마다 행동 버튼 1개(카카오 파트너센터 ‘내게 필요한 할 일’ 패턴). 예: 연결된 디자이너가 없는 판매 중 메뉴, 제공 메뉴가 없는 디자이너, 근무시간 밖·휴게와 겹친 이번 주 예약, 노쇼 이력 고객, 2주 안의 매장 휴무, 예약·결제 연동 상태.
- **이번 주 예약(막대, 앱/전화·방문 구분)·디자이너별 오늘(근무시간 대비 예약이 찬 비율, Fresha occupancy)·다음 예약(현재 이후 3건)·접수 준비(4단계 체크)·최근 활동(접수/완료/취소/노쇼 피드)·앱 리뷰(장소 연결 후 표시).** 홈에는 편집 폼을 두지 않는다(배민 조회/편집 분리 원칙).

### 예약 목록

- 기간 토글 오늘/이번 주/이달/지난 예약, 상태 탭에 건수, 디자이너·경로 필터, 이름·연락처·메뉴 통합 검색. 행: 일시 · 고객(연락처) · 메뉴(디자이너) · 경로 · 금액(예약금/현장 결제) · 상태. 행을 누르면 캘린더와 같은 상세 패널. 하단에 건수와 현장 결제 합계(노쇼·취소 제외).
- 예약번호는 상세에만 보조로 표시한다. 네이버의 ‘이용일/신청일 기준’ 전환은 신청 시각 데이터가 생기면 추가한다.

### 고객

- 고객은 예약 기록에서 연락처 기준으로 자동 생성된다(공비서·Fresha). 목록: 이름+태그(단골=방문 3회 이상/신규/노쇼 n회) · 연락처 · 방문 n회(최근 방문·메뉴) · 주 담당 · 다음 예약 · 메모 미리보기. 정렬: 최근 방문/방문 많은 순/노쇼 많은 순.
- 상세: 방문·노쇼·누적 결제, 주 담당, 자주 받는 메뉴, 다음 예약(→ 예약 상세), 업체 메모(고객 비공개), 예약·방문 이력, ‘이 고객 예약 추가’(캘린더 입력 폼에 이름·연락처·주 담당 자동 채움). 예약 상세의 고객 이름에서 1탭으로 진입한다(네이버 고객 상세 패턴).
- 연락처는 예약 안내 목적에만 쓰고, 마케팅 발송은 동의 체계가 생기기 전에는 제공하지 않는다. 재방문 주기 vs 매장 평균, 사진 첨부는 다음 단계.

### 통계

- 기간(이번 주/이달) KPI: 예약 수(취소 별도), 방문 완료율, 노쇼율, 현장 결제(방문 완료 기준). 카드: 디자이너별(예약·완료), 메뉴별(건수·매출), 예약 경로 비율, 시작 시간대 분포. 예약 연동 전에는 집계 화면 대신 안내만 보인다.

### 월간 보기·출근표 (2026-10-19 사용자 요청)

- **월간:** 7열 달력. 날짜마다 매장 휴무(빗금+사유), 출근하는 디자이너 아바타와 휴무 디자이너 이름, 예약 2건 미리보기 + ‘+N건’. 오른쪽 요약: 영업일·휴무일·예약 수·디자이너별 출근일. 날짜를 누르면 그날 일간(모바일은 목록)으로. 시안은 10월만 있어 이전/다음 달이 비활성.
- **출근표:** 행 = 매장·디자이너, 열 = 날짜. ● 근무 / 휴 / 매장 휴무(빗금, 누를 수 없음) / 날짜 예외는 노란 테두리 / 작은 숫자 = 그날 예약 수. 누르면 바로 바뀌고(근무 → 휴무, 정기 휴무 날은 ‘출근’ 예외) ‘이번 달 변경 되돌리기’로 한 번에 복구. 예약이 있는 날을 휴무로 바꿔도 예약은 남고 고객 연락을 안내. 서버의 날짜 예외(`overrides`: 날짜+hours+breaks)로 저장되며, hours가 비면 휴무·있으면 출근이므로 추가 스키마 없이 표현된다.
- **휴무 정하는 길은 세 곳:** 캘린더 빈 칸 › ‘이 날 휴무’, 출근표의 날짜 칸, 기본 근무시간 › 특정 날짜. 모두 같은 데이터다.

### 메시지 (2026-10-19 사용자 요청)

- 고객이 **앱의 예약 상세**에서 보내는 메시지를 관리자에서 실시간으로 받고 답한다. 목록(이름·읽지 않음·예약 요약·마지막 메시지·시간) → 대화(예약 카드 + 말풍선 + 빠른 답장 4개 + 입력). 예약 확정·변경·취소 자동 안내는 같은 대화에 시스템 메시지로 남는다. 예약 상세와 대화는 서로 오간다(예약 상세 ‘메시지’ 버튼 ↔ 대화의 ‘예약 상세’).
- 읽지 않은 대화 수는 메뉴 배지와 홈 할 일(‘답변을 기다리는 메시지 N건’)에 보인다. 모바일은 목록 → 대화 전환, 하단 탐색에 메시지.
- 범위: 예약에 묶인 대화만(자유 채팅 아님). 야간(22~09시)은 알림 없이 쌓임. 마케팅 발송 아님.
- **구현 가능성:** Supabase Realtime(이미 쓰는 Supabase)으로 `conversations`·`messages` 테이블 변경을 구독하면 양쪽이 실시간으로 받는다. 필요한 것: 두 테이블 + RLS(고객은 자기 예약 대화만, 업체는 자기 매장 대화만), 앱 예약 상세의 입력 UI, 사업자 푸시(앱/웹 푸시), 야간 알림 보류 규칙, 신고·차단. 예약 저장 테이블이 먼저 있어야 한다.

### 메뉴 사진 (2026-10-19 사용자 요청)

- 메뉴 목록 첫 열과 고객 미리보기의 메뉴 선택에 **사진 타일**(44px). 메뉴 편집 대화상자 맨 위에 ‘메뉴 사진 · 사진 올리기’(가로 4:3, 시술 결과 사진 권장). 사진이 없으면 카테고리 아이콘 타일(커트·펌/컬러·헤드스파·패키지). 실제 구현은 Supabase Storage 업로드 + 썸네일.

### 매장 정보 (2026-10-19 사용자 질문 “매장 정보를 바꾸면 상세페이지에 자동 반영되나”)

현재 앱의 장소 상세페이지는 리서치 파이프라인이 만든 정적 데이터(`lib/generated/*-places`)를 읽고, 업체 테이블(`merchants`)과 지도 장소 사이에 연결 키가 없다. 그래서 지금은 자동 반영이 아니다. 시안 v3.3은 연동 후 흐름을 세 단계로 나눈다.

- **설정에서 자동 반영**: 영업시간·휴무(기본 근무시간·출근표·캘린더), 메뉴·가격(판매 중만), 디자이너(담당자 선택형일 때). 매장 정보 화면에서는 확인만 하고 각 설정으로 이동한다.
- **저장하면 즉시 반영**: 전화번호, 영어 응대 가능, 임시 안내(60자, 상세페이지 상단 띠). 관광객에게 당장 중요하고 오입력 피해가 작은 항목만. 저장 즉시 고객 앱에 보인다.
- **운영팀 검수 후 반영**: 매장 이름(한·영), 주소, 소개(한·영), 사진. 요청하면 ‘검수 대기’로 쌓이고 그동안 기존 정보가 계속 보인다. 운영팀이 승인하면 상세페이지가 바뀌고 업체에 알린다. 요청 취소 가능. 영문 소개가 비면 운영팀이 번역한다. 주소가 바뀌면 운영팀이 지도 핀 위치를 확인한다.
- 오른쪽에 고객 앱 상세페이지 미리보기(사진·이름·평점·영업 상태·휴무·주소·전화·소개·메뉴·디자이너·예약 버튼)를 두고, 검수 중인 항목은 ‘검수 중’ 표시를 붙여 지금 보이는 값과 구분한다. 1160px 이하에서는 ‘수정/미리보기’ 전환.
- 홈 할 일에 ‘매장 정보 검수 대기 N항목’을 띄운다. ‘현재 제공 범위’에서는 연동 전 안내(운영팀에 요청 → 데이터 수정 → 배포 1~2분)를 보여준다.

실제 구현에 필요한 것: (1) `merchants`↔장소 id 연결 컬럼과 운영팀 승인, (2) 업체가 고칠 수 있는 항목과 즉시/검수 구분의 확정, (3) 상세페이지가 정적 데이터 위에 DB 값(즉시 항목·승인된 검수 항목)을 덮어쓰도록 변경(ISR 재검증 또는 클라이언트 조회), (4) 운영팀 콘솔의 검수 큐(1단계는 수동 가능), (5) 사진 Storage 버킷. 네이버 스마트플레이스가 신규 상품을 검수 후 노출하는 것과 같은 이유로 이름·주소·사진은 검수형으로 둔다.

### 결제·환불 상태와 월 정산 (2026-10-19 저녁, 시안 v3.4 · 돈의 흐름 결정 전 예시)

운영 요건 검토의 기본안(플랫폼이 예약금을 받고 월 정산, 정액 1만 원, 업체 취소는 전액 환불, 고객 취소는 전날까지 전액·당일 0%)을 가정한 화면이다. 결정이 바뀌면 숫자와 문구만 바꾼다.

- 예약 상태와 결제·환불 상태를 분리해 보여준다. 예약 상세·예약 목록·정산에 같은 칩을 쓴다: 예약금 결제 완료(확정) / 예약금 차감 완료(방문 완료) / 예약금 업체 귀속(노쇼) / 전액 환불 처리 중 → 완료(업체 취소·전날까지 고객 취소) / 환불 없음 · 업체 귀속(당일 고객 취소) / 현장 결제(예약금 없음).
- 업체가 취소하면 사유와 관계없이 전액 환불이 자동으로 시작되고 ‘처리 중’으로 보인다(카드사 반영 3~7영업일).
- 정산 화면(매장 › 정산): 월 선택. 집계 중인 달은 예약금 수납·환불·정산 대상·지급 예정(수수료 차감) KPI와 예약별 명세(일시·고객·메뉴·예약 상태·결제·환불·정산 대상), 아직 방문 전인 예약금과 현장 결제 예정액은 따로 안내. 지난달은 지급 완료 예시와 명세서 PDF·세금계산서 자리. 분쟁 중인 예약은 지급 보류. 현장 결제는 정산에 포함하지 않는다.
- ‘현재 제공 범위’에서는 연동 후 집계 안내만 보인다. 수수료율은 미정이라 ‘예시 10%’로 표기한다.

### 영문 이름 (2026-10-19 저녁, 시안 v3.4)

고객 앱은 영어가 기본이므로 메뉴와 디자이너에 영문 이름을 둔다. 메뉴 편집기에 ‘메뉴 이름(영문)’, 담당자 기본정보에 ‘영문 이름·영문 소개’. 고객 미리보기와 매장 정보 미리보기는 영문을 먼저 보여주고 한글을 작게 붙인다. 영문이 비면 한글로 보이고, 홈 할 일에 ‘영문 이름이 없는 메뉴 N개’가 뜬다(운영팀 번역 전까지). 서버에는 `merchant_services`·`merchant_staff`에 영문 컬럼이 필요하다.

### 메뉴·패키지

- 카테고리/판매 상태 필터, 메뉴명 검색, 가격/시술+정리 시간/담당자/상태 열.
- 상세는 이름·설명·카테고리 → 총 가격·시간 → 제공 담당자 → 판매 상태 순서.
- 한국어·영어는 같은 메뉴의 언어별 입력을 접어 표시한다. 한쪽을 잃지 않는다.
- 단일 방문 묶음 패키지임을 안내한다. 회차권·담당자별 자동 가산은 지원하지 않는다.
- 기본정보 저장과 담당자 연결은 현재 서로 다른 명령이다. 한 번에 모두 저장된 것처럼 표시하지 않는다. 메뉴 저장 후 연결 단계별 결과를 안내하거나 기존 단건 연결을 유지한다. 배치 API 없는 상태의 가짜 원자적 저장을 금지한다.

### 담당자

- 왼쪽 목록에 **원형 프로필 사진**·이름·직함·제공 메뉴 수·신규 예약 노출 상태. 선택 시 오른쪽 상세. 사진은 기본정보 탭에서 올리며(정사각형 권장) 캘린더 열 머리·디자이너 칩·고객 앱의 디자이너 선택·예약 상세에 같은 사진이 쓰인다. 사진이 없으면 담당자 색의 실루엣(머리 모양 3종)으로 대신한다. 시안은 실존 인물 사진을 쓰지 않는다.
- 기본정보 / 제공 메뉴 / 근무 일정은 독립 탭이며 저장 범위가 다름을 명시한다.
- 기존 API를 우선 재사용한다. 제공 메뉴는 단건 연결·해제의 pending/실패/결과 미확인 상태를 각 항목에 표시한다.
- 근무 일정 탭과 예약 가능 일정의 해당 담당자 선택은 같은 서버 레코드와 편집 컴포넌트를 쓴다. 별도 시간표 복사본을 만들지 않는다.
- 담당자를 쓰지 않는 숍은 담당자 입력을 필수로 하지 않는다. 앱의 담당자 단계도 생략한다.

### 기본 근무시간 (예약 캘린더의 반복 규칙)

- 매장 공통/담당자 선택 후 ‘매주 반복’과 ‘특정 날짜’로 분리한다.
- 주간 요약은 7일을 빠짐없이 표시한다. 미설정과 휴무를 구별한다. 요일 편집에서 영업/근무 시간과 휴게시간을 입력한다.
- 같은 시간을 평일·선택 요일로 복사한다. 저장하기 전 적용 대상을 보여주며 숨은 자동 저장은 하지 않는다.
- 특정 날짜는 달력에서 선택 → 휴무 / 다른 영업시간 / 일부 시간 차단 중 선택 → 해당 날짜의 예외 저장. 기존 예외도 확인·수정·해제할 수 있어야 한다.
- 우선순위: 날짜별 특별 영업/휴무가 해당 대상의 반복 규칙을 대체하고, 차단은 그 안에서도 시간을 제외한다. 담당자 가능 시간은 매장 가능 시간과 교집합이다. 매장 수용량·기존 예약·결제 대기 점유까지 서버가 함께 검증한다.
- 담당자 화면에서 허용된 시간을 매장 영업시간으로 확대한다고 오해하지 않도록 매장 규칙과 최종 가능한 시간을 구별한다.
- 월간 반복·격주·공휴일 자동 규칙은 현재 서버 지원을 확인하기 전 UI에 넣지 않는다.

### 고객 예약 화면 확인 (디자이너 선택)

- 2026-10-19 확인: 서버 설계는 디자이너 선택을 지원한다(예약 방식 `staff`/`shop`, 담당자·담당자별 제공 메뉴·근무 일정 저장). **고객 앱의 현재 예약 화면(`components/booking/booking-sheet.tsx`)은 고정 데이터 데모라 디자이너 선택 단계가 없고 관리자 데이터와 연결돼 있지 않다.**
- 담당자 선택형: 메뉴 → 그 메뉴를 하는 디자이너(소개·가장 빠른 예약 시간) → 날짜·시간 → 금액·정책 확인. 첫 버전은 직접 선택만, ‘아무나 배정’ 없음(승인된 운영 설계와 동일).
- 매장 예약형: 메뉴 → 날짜·시간 → 확인. 디자이너 단계를 생략한다.
- 빈 시간은 캘린더와 같은 데이터로 계산한다: 매장 일정 ∩ 디자이너 근무 − 휴게·막은 시간·기존 예약, 동시 예약 수 이하, 시술+정리 시간이 들어가는 30분 단위 시작, 당일은 현재+60분 이후.
- 시안의 ‘시안 예약 넣어 보기’는 고객 화면에서 고른 예약이 관리자 캘린더의 해당 디자이너 열에 앱 예약으로 들어가는 연동을 보여주는 설명용이다. 접수 전(현재 제공 범위)에는 확정할 수 없다.

## 저장·오류·이동 공통 규칙

1. 편집 중인 대상과 범위를 고정 표시한다. 화면 하단의 저장 영역은 스크롤해도 접근 가능하게 한다.
2. 저장 전 dirty, 저장 중 pending, 성공 후 서버 확인, 오류 후 입력 보존을 구별한다.
3. 버전 충돌은 덮어쓰지 않고 최신 값과 내 입력 비교/다시 불러오기를 제공한다.
4. 응답 유실은 ‘저장 결과 확인 필요’로 표시하고 동일 명령 재시도·재조회 경로를 유지한다.
5. 일부 명령 성공/후속 조회 실패를 전체 실패나 전체 성공으로 바꾸지 않는다.
6. 탭·담당자·메뉴 이동, 뒤로가기 때 미저장 입력을 보호한다. 다른 매장/계정의 초안을 재사용하지 않는다.
7. 조회 실패를 빈 목록·미설정 시간표로 위장하지 않는다. stale 표시는 마지막 조회 시각과 재시도를 제공한다.
8. 접수 활성 중 지원하지 않는 편집, 읽기 전용 매장, 권한 회수 등 기존 서버 제한은 그대로 안내한다.

## 레이아웃·접근성

- 데스크톱: 204px 탐색 + 가변 본문, 작업 공간 최대 1600px. 불필요한 외곽 여백 축소.
- 목록+상세는 충분한 너비에서만 나란히 표시한다. 좁으면 목록→상세. 일정의 편집은 보조 패널로 열어 긴 폼 누적을 막는다.
- 모바일: 간결한 상단, 하단 업무 탐색, 당일 목록 우선. 7열 시간표를 축소하지 않고 요일별 행으로 전환한다. 저장 영역과 하단 탐색이 가리지 않게 안전 영역을 확보한다.
- 본문 16px, 조밀한 보조 정보 14px 이상, 제목 24px. 한글 산세리프. 숫자 정렬, 44px 터치 영역, 텍스트+색 상태, 가시 포커스, 실제 label, 확대/키보드 접근.
- **시각 언어(국내 관리자 대시보드 공통 문법, 2차 조사 6절):** 페이지 바탕 `#f3f5f7`, 카드 흰색 + 1px hairline `#e6eae8` + radius 14px + 그림자 `0 1px 2px 4%`, 액센트는 브랜드 민트 `#0c8e70` 하나, 의미색은 칩·델타·막대에만. 서체 Pretendard Variable(없으면 Apple SD Gothic Neo), 본문 15px, 제목 22px, KPI 숫자 28px, 숫자는 tabular-nums. 상태 칩은 틴트 배경+같은 계열 글자(확정 민트/방문 완료 파랑/노쇼 빨강/취소 회색).
- 시안은 라이트만 제안한다. 실제 적용 시 프로젝트의 다크 모드 토큰·WCAG AA 대비를 검증한다. 경쟁사 로고/화면 자산을 복사하지 않는다.

## 시안과 실제 구현의 경계

검토 파일: `docs/designs/partner-admin-redesign-20261019/index.html`. 모든 상호·이름·메뉴·금액·날짜·예약은 설계 예시다. 브라우저 메모리에서만 동작하며 서버 저장·고객 예약 생성·결제·환불을 하지 않는다. ‘시안 적용’은 제품의 저장 성공이 아니다. 새로고침으로 초기화된다.

시안의 날짜별 내부 메모는 제안 항목이다. 현재 저장 계약 지원 여부를 확인해 지원 전에는 실제 편집 필드로 출시하지 않는다. 모바일 레이아웃과 고객 흐름 대화상자는 헤드리스 브라우저로 검증했고, 실기기·화면 낭독기 검증은 남아 있다. [확인 기록](../../../reports/design/2026-10-19-partner-admin-preview-check.md)을 참조한다.

## 구현 순서 제안

1. 시안 검토 후 공통 shell/탐색/타이포/목록-상세/독립 탭과 예약 캘린더(일간·주간·모바일 목록)를 현재 API의 근무·휴게·막은 시간·날짜 예외에 연결한다.
2. 반복 일정과 날짜 예외 편집기를 기존 검증·버전·재시도/초안 보호에 연결한다.
3. 메뉴와 담당자 연결, 고객 권한 가용 시간 조회의 일치 여부를 검증한다.
4. 별도 예약·결제 연결 작업에서 예약 저장(앱 예약 + 업체 입력 전화·방문 예약)과 상태 처리/금액을 연결하고, 고객 앱 예약 화면에 디자이너 선택 단계를 실제 데이터로 붙인다. 현재 서버에는 예약 저장 테이블과 업체별 고객 테이블이 없다. 홈 KPI·예약 목록·고객·통계·최근 활동은 모두 이 저장소 위에서 집계하므로, 그 전에는 ‘현재 제공 범위’ 화면(설정 기반 할 일·접수 준비만)을 보여준다.
5. 알림(사장님·담당 디자이너 푸시, 고객 리마인드 전날 18시·3시간 전, 야간 미발송)은 발송 채널 승인 후 구현한다.
6. 매장 정보 연동: 업체↔장소 연결, 즉시 반영 항목(전화·영어 응대·임시 안내)의 DB 덮어쓰기, 검수 큐. 예약 저장 테이블과 독립이라 먼저 할 수 있다(관광객에게 영업시간·임시 휴무·전화가 당장 유용).
7. 업체 시나리오 테스트와 사용자 최종 검토 후 배포 여부를 결정한다. 이 문서는 배포 승인이 아니다.

## 승인 전 확인할 질문

0. 홈 KPI 4개(오늘 예약/방문 완료/노쇼/현장 결제 예정)와 할 일 항목이 사장님이 아침에 보고 싶은 것과 맞는가. 고객 연락처·메모를 우리 서버에 보관하는 정책(보관 기간, 마스킹)은 운영팀 확인이 필요하다.
1. 예약 캘린더 구조(일간=디자이너별 열, 주간=요일 열, 모바일=목록 우선)가 숍 업무에 맞는가.
2. 업체가 직접 넣는 예약이 근무시간 밖이거나 휴게와 겹칠 때 경고 후 허용할지, 막을지. 시안은 경고 후 허용, 다른 예약·막은 시간과 겹치거나 휴무일이면 막는다.
3. PC 초기 설정 + 모바일 당일 처리 가정이 맞는가.
5. 정산 화면의 가정(플랫폼 수납·월 정산·수수료 예시 10%·익월 10일 지급)이 결정과 맞는가. 결정 전까지는 ‘기본안 예시’ 표기를 유지한다.
4. 매장 정보 중 업체가 직접 고칠 항목과 즉시/검수 구분(시안: 전화·영어 응대·임시 안내는 즉시, 이름·주소·소개·사진은 검수)이 맞는가. 검수 응답 기준(시안 1영업일)이 운영팀 인력에 맞는가.

내부 마메드네 매뉴얼은 로그인 접근 자료가 없으므로 미확인으로 남긴다.
