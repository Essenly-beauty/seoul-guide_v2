# MYSEOULDROP 다국어 운영 계획

> 상태: 제안 및 출시 준비 기준 (2026-08-17)  
> 제품 기본 언어: 영어(EN) · 대상: 서울을 방문하는 해외 사용자

## 결론

다국어 UI는 **구현 가능하지만 아직 제품에 국제화(i18n) 구조는 없다.** 현재 화면 문구는 TSX에 영어로 직접 들어 있고, 루트 HTML도 `lang="en"`으로 고정되어 있다. 다만 장소 데이터는 이미 영문 표시명 `name`과 네이버지도 검색용 한글 원문 `nameKr`·`address`를 분리해 두었으므로, 데이터 원장을 바꾸지 않고 UI와 콘텐츠 번역층을 추가할 수 있다.

첫 확장 언어는 다음 순서를 권장한다.

| 단계 | 서비스 UI | 이유 |
|---|---|---|
| 기본 | English (`en`) | 현재 기본값이며 모든 공개 콘텐츠의 기준 원문 |
| 1차 | 日本語 (`ja`), 简体中文 (`zh-CN`), 繁體中文 (`zh-TW`), ไทย (`th`) | 현재 온보딩에서 이미 주요 방문 국가로 묻고 있는 일본·중국·대만·태국 사용자를 직접 커버 |
| 2차 | 한국어 (`ko`) | 국내 파트너·운영 화면 및 한국인 사용자를 위한 선택지. 해외 방문자용 핵심 출시를 늦추지 않음 |

네이버지도 앱은 한국어·영어·중국어(간체)·일본어를 지원하지만, **MYSEOULDROP 링크가 언어를 강제할 수는 없다.** 사용자의 네이버지도 앱 설정을 따라야 한다. 대신 장소 검색/길찾기에는 오인식 위험이 낮은 한글 원문 이름을 계속 전달한다.

## 언어와 국가를 분리한다

- `countryCode`는 방문자 국가·세금환급·여행 맥락을 위한 정보다. UI 언어를 자동으로 바꾸는 근거가 아니다.
- UI locale은 브라우저 `Accept-Language`로 제안하고, 사용자가 언제든 직접 바꿀 수 있게 한다.
- 현재 프로필의 `preferredLang`은 “매장에서 사용할 언어”라는 뜻이다. UI locale 필드와 혼용하지 말고, i18n 도입 시 `visitLanguage`와 `uiLocale`을 별도 값으로 관리한다.
- 장소의 공식 한글 상호·주소·좌표·검증 출처는 번역하지 않는 원장 데이터다. `nameKr`은 네이버지도 링크와 운영 확인에 계속 사용한다.

## 권장 기술 구조

### URL과 선택 규칙

영어 공개 URL은 지금처럼 유지해 기존 공유 링크를 깨지 않는다. 새 언어만 locale prefix를 사용한다.

| 화면 | URL 예시 |
|---|---|
| 영어 기본 | `/map`, `/place/hosu-dosan` |
| 일본어 | `/ja/map`, `/ja/place/hosu-dosan` |
| 중국어 간체 | `/zh-CN/map` |
| 중국어 번체 | `/zh-TW/map` |
| 태국어 | `/th/map` |

최초 방문에는 `Accept-Language`와 브라우저 저장 설정으로 제안하되 자동 리다이렉트는 한 번만 한다. 공유 링크·검색엔진·이메일 링크의 명시 locale이 항상 우선이다.

### 메시지와 데이터

1. 화면 문구를 `messages/en.json`의 안정적인 키로 이동한다. 예: `map.search.placeholder`, `auth.signIn.google`, `place.directions.naver`.
2. 같은 키 세트를 `ja`, `zh-CN`, `zh-TW`, `th` 파일에 유지한다. 누락 키·영문 폴백·사용하지 않는 키는 CI에서 실패시킨다.
3. 숫자·날짜·통화는 하드코딩하지 않고 locale formatter를 쓴다. 실제 판매 가격·원화 표기는 원문 금액과 `KRW`를 보존한다.
4. 장소·서비스·블로그는 원장과 번역을 분리한다.

```text
places (원장)
  id, name_ko, address_ko, latitude, longitude, source_url, verified_at

place_translations
  place_id, locale, display_name, summary, tags, service_labels,
  reviewed_at, reviewer, source_revision
```

사업자가 쓰는 공식 명칭과 사용자 리뷰 원문은 덮어쓰지 않는다. 리뷰는 원문을 먼저 보여 주고, 필요할 때만 “번역 보기”를 사용자 동작으로 제공하며 자동 번역임을 표시한다.

### SEO·외부 채널·알림

- locale별 `<html lang>`, title, description, Open Graph, sitemap, `hreflang`, canonical을 함께 생성한다.
- 가입/비밀번호 재설정/운영 안내 이메일도 UI locale을 저장해 그 언어로 보낸다. 법무·개인정보·의료 표현은 기계 번역만으로 발행하지 않는다.
- 앱스토어/Play 스토어 설명·스크린샷은 웹 UI 번역과 별도 릴리스 항목으로 관리한다.

## 효율적인 운영 방식

### 번역 원장과 검수

- **영어를 source locale**로 삼고, 번역 키·용어집·변경 이력을 Git에서 버전 관리한다.
- K-beauty, 시술, 세금환급, 지하철, 예약·환불 용어는 언어별 용어집에 먼저 확정한다. 같은 용어가 화면·블로그·메일에서 다르게 번역되지 않게 한다.
- AI 초안은 반복 UI·비법적 콘텐츠에만 사용하고, 1차 언어권의 자연스러운 문장 검수자가 publish 승인한다.
- 장소 데이터가 바뀌면 `source_revision`을 올리고 그 장소의 번역만 재검수 대기열에 넣는다. 전체 문서를 다시 번역하지 않는다.
- 긴 문장·중국어 글자·태국어 줄바꿈을 포함한 locale별 스크린샷 검사를 배포 게이트로 둔다.

### 변경 주기와 우선순위

| 콘텐츠 | 책임 | 게시 기준 |
|---|---|---|
| 네비게이션·로그인·오류·설치 안내 | 개발 + AI 초안 + 언어 검수 | 모든 배포에서 번역 키 100% 충족 |
| 장소명·주소·시간·가격 | 데이터 운영 | 한글 원장 검증 후, UI 번역은 지연 가능하되 원문과 검증일 표기 |
| 블로그·SEO | 콘텐츠 운영 + 언어 검수 | 언어별 독립 발행 상태. 미번역 글은 해당 locale에서 숨기거나 영어 원문임을 명확히 표시 |
| 약관·개인정보·의료/광고 문구 | 법무 + 전문 번역 | 국가별 승인 전 게시 금지 |
| 사용자 리뷰 | 사용자 원문 보존 | 필요 시 사용자 요청형 번역만 제공 |

|---|---|---|---|
| 0. 범위 확정 | 모든 문자열·메일·메타데이터·법무 문구를 수집해 번역 인벤토리 생성 | 1차 언어 4개와 출시 지역 확정 | 키 목록과 미번역 목록 |
| 1. 기반 구현 | locale 라우팅, 메시지 로더, 언어 선택기, 저장/폴백, 형식화·SEO 구조 구현 | 번역 톤·용어집 승인 | 영어 링크 유지 + 각 locale 경로 E2E |

| 3. 콘텐츠/데이터 | 장소·서비스·블로그 번역 테이블, 수정 대기열, 검증일 UI 구현 | 공식 상호·의료/가격 표현·법무 문안 승인 | 원장 변경이 해당 번역 대기열만 만드는지 확인 |
| 4. 운영 자동화 | 누락 키·용어집 위반·locale별 링크·메타데이터 검사와 번역 PR 템플릿 구축 | 발행 책임자와 SLA 확정 | CI 통과, 주간 번역/검수 리포트 |

## 출시 게이트

1. 1차 대상 locale에서 핵심 공개 흐름(지도 → 검색 → 장소 → 외부 지도 → 설치 안내)이 실제 기기에서 통과한다.
2. 영문 기본 URL과 기존 공유 링크가 그대로 작동하며 locale 변경 후에도 목적지를 잃지 않는다.
3. 한글 상호·주소를 네이버지도에 전달해 실제 장소가 열리는지, 영어 설정 네이버지도에서도 확인한다.
4. 자동 번역·원문·사람 검수본의 상태가 운영 도구에서 구분된다.
5. locale별 접근성(스크린리더 언어, 확대, 줄바꿈)과 법무 문구가 승인된다.

## 이번 변경의 범위

이번 배포는 네이버지도 버튼을 모바일에서 실제 NAVER Map 앱으로 연결하고, 앱의 언어 선택권은 사용자 설정에 남긴다. UI 전체를 다국어화하는 대규모 변경은 위 0~4단계 승인 뒤 별도 릴리스로 진행한다.
